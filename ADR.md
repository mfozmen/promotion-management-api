# Architecture Decision Records

This document records the significant architectural decisions made for the ModaCo Promotion Management API. Each ADR captures the context that prompted the decision, the decision itself, and its consequences and trade-offs, so future contributors understand not just what was decided but why.

---

## ADR-0001: Node.js, Express and TypeScript

**Status:** Accepted — mandated by the case study

### Context

The case study specifies the implementation stack: Node.js, Express, and TypeScript. No alternative runtime or framework evaluation is required or expected.

### Decision

Build the API on Node.js 22 (current LTS-track version), using Express 5 as the HTTP framework, with TypeScript in strict mode for all source code.

### Consequences

- Express 5 brings native support for async route handlers (unhandled rejections are forwarded to error middleware automatically), simplifying error handling compared to Express 4.
- TypeScript strict mode catches null/undefined and type-mismatch bugs at compile time, at the cost of more upfront type annotation work.
- The ecosystem (middleware, testing tools, ORMs) for Node/Express/TypeScript is mature and well-documented, reducing integration risk.
- Because the stack is mandated rather than chosen, there is no trade-off analysis against alternatives (e.g. Fastify, NestJS) — that discussion is out of scope.

## ADR-0002: Test-driven development with Vitest

**Status:** Accepted

### Context

The case study requires a TDD workflow. A test runner and assertion/mocking toolkit compatible with TypeScript and Express (via Supertest for HTTP-level tests) is needed, with fast feedback loops given the red-green-refactor cycle will run continuously during development.

### Decision

Use Vitest as the test runner, paired with Supertest for HTTP integration tests against the Express app. Every feature and bug fix starts with a failing test written before the implementation.

### Consequences

- Vitest's native TypeScript/ESM support avoids extra transpilation configuration and its watch mode gives sub-second feedback, which is important for a strict red-green-refactor cycle.
- Supertest lets integration tests exercise the Express app in-process (no network binding required), keeping the hottest endpoints (e.g. single product detail) testable at both unit and HTTP-contract level.
- Coverage reporting (`npm run test:cov`) feeds the SonarCloud quality gate.
- TDD discipline slows down initial feature authoring in exchange for a regression-resistant codebase and living documentation of behavior via tests — this is treated as a net win for a codebase reviewed by AI and humans on every PR.
- Database tests run against a real PostgreSQL, never a mock or an in-process substitute, because the invariants under test are `CHECK`, unique and GiST exclusion constraints that only PostgreSQL enforces. The cost is a `postgres:16-alpine` service in CI and a running server locally (`TEST_DATABASE_URL`); isolation comes from cloning a migrated template database per test file.
- The clone-per-file scheme costs one `drop database` per file at teardown, and each forces a cluster-wide checkpoint and fsync (~620 ms, measured at teardown on a written-to database dropped `with (force)` after a pool has been open, against ~37 ms to clone the template; dropping an untouched clone is an order of magnitude cheaper, so the figure does not reproduce outside the harness), so the integration project's `hookTimeout` is sized for the teardown rather than the setup. That is linear in the number of integration test files; past roughly a dozen the answer is `fsync=off` on a throwaway test server, not a longer timeout.
- Test databases are named for the sweep that collects them. `pg_database` records no creation time, and a clone has no connections until its lazily-connecting pool issues a first query, so "no connections" cannot tell an abandoned clone from one a `beforeAll` just created: the clone's own name carries the epoch and age is the only discriminator, with an hour as the slack. The migrated template is named after the checkout (`sha256(cwd)`) rather than per run, because `tests/integration/env.ts` is loaded independently by the setup process and by every worker and the name has to come out the same in all of them; a per-run template would be one naming scheme instead of two and would need no forced drop, but it would have to reach the workers through Vitest `provide`/`inject`. Accepted costs: a deleted worktree's template survives on the server for ever (the sweep deliberately never matches a template name), and the template is dropped with `(force)`, so one worktree runs one integration suite at a time — README says so.
- The suite is two Vitest projects (`vitest.workspace.ts`): `unit` needs no service and is what `npm test` and the pre-commit hook run, `integration` carries the database `globalSetup` and is what CI and the pre-push agents run. Without the split every `git commit` on every branch would need a live PostgreSQL; with it the 100 % coverage gate moves from the hook to the required `ci` check, which runs both projects (owner decision, 2026-09-12).

## ADR-0003: PostgreSQL write store, Redis read model, BullMQ event queue (CQRS)

**Status:** Accepted — see `docs/superpowers/specs/2026-09-12-domain-design.md`

### Context

Two workloads pull in opposite directions: the storefront reads (`GET /products`, `GET /products/:id`) must survive flash-sale traffic, while admin writes and weekly bulk ingestion must remain transactional and race-free. A single relational store serving both would put the hottest endpoint in the system behind the same connection pool as 500 000-row imports.

### Decision

CQRS on a modular monolith. PostgreSQL 16 is the write store and the only source of truth, accessed through Drizzle ORM with SQL migrations (which double as the DDL deliverable). Redis 7 holds the read model the storefront queries: a hash per product and price-ordered sorted sets per category and for all products. BullMQ, running on a separate Redis logical database, carries events from writes to the queue workers, which recompute affected read-model entries from PostgreSQL. One Docker image runs four commands: `api`, `event-handler`, `ingestion-worker`, `reconciler`. Four commands against four queues is not one-to-one: `event-handler` runs the `promotions` and `catalog` Workers in one process, `ingestion-worker` runs `ingestion`, and `reconciler` runs `maintenance` plus its own repeatable schedule.

Money is stored as integer minor units, percentages as basis points, timestamps as `timestamptz`.

Locally both stores run from `docker-compose.yml` (`postgres:16-alpine` and `redis:7-alpine`, healthchecked, on named volumes and a named network, with Adminer and redis-commander behind the `tools` profile) beside the `api` service described below; the worker containers and the `monitoring` profile are not built yet. The application takes its wiring from the environment — `DATABASE_URL`, `REDIS_URL` and the two logical-database indexes `REDIS_READ_MODEL_DB` (read model) and `REDIS_QUEUE_DB` (BullMQ) — documented in `.env.example` and read by `loadConfig` in `src/shared/config.ts`, a zod schema `src/server.ts` calls before anything else, so a missing or malformed value stops the process instead of the first query. Beyond typing and defaults it checks only the three mistakes that would otherwise surface late and quietly: a `DATABASE_URL` carrying no database name, the read model and the queue on the same logical database, and `INGESTION_LEASE_MS` below `INGESTION_BUDGET_MS`; everything else fails on its own at first use. The module that opens a Redis connection derives its URL from `REDIS_URL` plus the index. `src/server.ts` is its first consumer: it takes `DATABASE_URL` for the boot migration and `PORT` for `listen`, so there is no second place reading either. The connection URLs are the only source of truth for where the application connects. The database name is required because node-postgres would otherwise fall back to `PGDATABASE`, then the user name, then the OS user, so an omitted name connects to something and the mistake surfaces later as missing tables. `REDIS_URL` needs no equivalent check: the index, not the URL path, picks the logical database. `docker-compose.yml` publishes 5432, 6379 and 3100 on `127.0.0.1` as literals rather than through `POSTGRES_PORT` and `REDIS_PORT` overrides, and nothing must reintroduce those two variables: they are the names Kubernetes injects for Services called `postgres` and `redis`, in the form `POSTGRES_PORT=tcp://10.96.1.5:5432`, so they are not ours to read. A cross-check against a variable this application does not own adds a failure mode and buys nothing — it briefly did, and with a sidecar proxy making `DATABASE_URL` loopback it would have crash-looped every pod in the namespace at startup, blaming a compose file that deployment never had. A developer whose 5432 is occupied edits the compose file and the URL together.

Four settings in that file are deliberate and would otherwise look arbitrary. Redis runs with `--appendonly yes`, because the queue database holds jobs that must survive a restart of the container, and with no `maxmemory`, so the default `noeviction` policy holds: the read model carries no TTL by design and must never be silently evicted. PostgreSQL runs with `log_lock_waits=on` and `deadlock_timeout=200ms`, because the defaults (off, 1 s) would let the deadlock scenario report "no deadlock" from a run that never looked. Every published port binds `127.0.0.1`, including the two `tools` browsers, so a laptop on a shared network offers neither a database nor a browser for one. `rediscommander/redis-commander` is the one unpinned image: the publisher ships no version tags at all, only `latest` and a few branch tags, and the container is dev-only behind the profile. Adminer stands in for the pgAdmin the case study names as an example, being one container with no setup.

A third service, `api`, is built from the `Dockerfile` in this repository and is what makes a plain `docker compose up -d --wait` mean "migrated and serving". Its entrypoint runs the migrations (`src/shared/db/migrate.ts`, `drizzle-orm`'s own migrator) and only then listens, so the healthcheck compose waits on cannot answer in front of a schema that is not there. The image is multi-stage: a build stage compiles TypeScript, and the runtime stage carries `dist/`, production dependencies and the migration SQL, which the migrator reads at run time rather than compiling in. `drizzle-kit` stays a devDependency and out of the image, so nothing reaches the registry at container start. Verified from empty volumes: `up -d --wait` returned 0 with the six tables and `__drizzle_migrations` in place and `/health` answering; it is idempotent because `__drizzle_migrations` records what has been applied, so every `up` brings the schema current with nothing for an operator to remember.

It was first a separate one-shot `migrate` service, so that `docker compose up -d --wait` alone would leave a migrated schema in place, which is what the owner asked for, and that does not work: **`--wait` has no way to express "this one finished".** Its contract is "running, or healthy where a healthcheck exists", and a one-shot is neither of those for long, so it fails in both directions. Both measured on Compose v5.5.0. _False failure:_ a one-shot that has already exited counts as a wait failure whatever its status, so a fast migration makes a completely healthy stack exit 1. _False success, which is the dangerous half:_ a one-shot still running satisfies `--wait`, so with the real command (`npm ci` then `drizzle-kit migrate`, 9.4 s) `up -d --wait` reported the container healthy and exited 0 while the migration was still installing — and exited 0 again over a migration headed for an authentication failure. That measurement is why the schema belongs to a long-lived service with a healthcheck rather than to any one-shot, and the owner has ruled the one-shot shape out for good: no standalone migration service, and nothing later gates on `service_completed_successfully`; anything that needs a migrated database gates on `api` being healthy.

What the api-migrates shape costs, since the one-shot it replaced is not strictly worse everywhere. The one-shot had one serialisation point for free: one container migrated and `service_completed_successfully` gated the rest. This shape has none, so **the schema belongs to `api` alone** — `api` is single-replica, and nothing else shipping this image may call `runMigrations`; whether the event handler, ingestion worker and reconciler ever do is not decided yet, and the day one of them does, a `pg_advisory_lock` around the call stops being optional. `--wait` is also a compose verb no production deploy uses: on a rolling Kubernetes deploy, whose default surge starts new pods beside old ones, N pods migrate at once while the old pods query the old schema. That is the one case where the rejected alternative was better, and it is not a case this repository deploys into. The image carries no `HEALTHCHECK` of its own either, so a deploy outside compose needs its own readiness probe. The compose healthcheck runs `node -e fetch(...)` rather than `curl` or `wget`, because the alpine runtime image ships neither and adding one to the image for a healthcheck is a package more than the application needs.

Three properties of that boot are easy to read as stronger than they are. `lock_timeout` is **per lock acquisition, not per boot**: migration `0000` alone is about forty statements, so a contended migration can wait forty times ten seconds, which is longer than the `start_period` — the 180 s is the budget a healthy migration has, and the lock timeout only stops any single wait being unbounded. It is set with `set lock_timeout` on connect rather than in the connection `options`, because `pg` lets a `DATABASE_URL` carrying its own `options` replace them wholesale and say nothing, which managed PostgreSQL and pgbouncer both do routinely. And `start_period` is free on the success path and not on the failure path: `restart: unless-stopped` restarts the period on every attempt and failures during it never count toward `retries`, so a container crash-looping early never reaches `unhealthy` and `--wait` has no bounded failure of its own — hence `--wait-timeout` in the documented command. The drift ADR-0003 already admits the healthcheck cannot catch, a password changed against an existing volume, is exactly the case that arrives this way.

One more route to the skip hazard above, because the journal test cannot see it: two containers from different images calling `runMigrations` at once. The migrator reads the last applied row **before** it opens its transaction, so both read the same row, the loser fails on `CREATE TYPE`, restarts, and now finds a `created_at` newer than its own entry — skipping its migration and reporting success. An advisory lock would only make the loser wait before doing the same thing. What stops it is the constraint being enforced rather than written: `tests/unit/shared/db/migrate-callers.test.ts` fails on the branch that adds a second caller under `src/`, which is where the alarm is useful. The branch that adds the first worker command to this image carries that guard forward or takes the lock instead.

Two more properties worth stating because nothing in the code says them. All pending migrations run in **one transaction**, so the set is atomic and not resumable: a migration killed at minute nine costs nine minutes again on the next boot, every boot, and the operator reflex of tearing a slow boot down makes the failure stable rather than self-healing. And the healthcheck's `start_period` is a **migration-duration budget**, not a boot budget — a migration expected to outlast it raises it in the same pull request, which is free because the first passing check ends the start period.

The application listens on 3100 rather than 3000. The default port of every other Node service on a developer's machine is 3000, and on this one it was already taken by an unrelated container, so a fixed 3000 meant the stack could not come up at all. `PORT` is still the knob; 3100 is only the default, and the compose file publishes it on `127.0.0.1`.

The compose file states what runs; why any of it runs that way is here.

The PostgreSQL healthcheck runs a real `psql` query rather than `pg_isready`, which only sends a startup packet and reports "accepting connections" (exit 0) for a database that does not exist. Measured against this stack: `pg_isready -U promo -d nosuchdb` exits 0, the `psql` check exits 2. What it catches is a **database name or role** that no longer matches an already-initialised volume, which is the drift `depends_on: service_healthy` would otherwise start a crash loop behind.

It does **not** catch a changed `POSTGRES_PASSWORD`, and nothing in the container can. The image generates `pg_hba.conf` at volume initialisation with `local all all trust` and `host all all 127.0.0.1/32 trust`, so a healthcheck running inside the container never authenticates whichever way it connects, and the file is not regenerated for an existing volume. A password changed in `.env` against a populated `postgres-data` therefore still reports healthy; it surfaces at the first consumer's connect as `password authentication failed`, and the operator's fix is `docker compose down -v`. `psql` reads the user and database from the container's own environment and is passed no password at all, so nothing secret reaches the process list.

### Consequences

- Storefront reads never touch PostgreSQL; their cost is one or two Redis round trips regardless of promotion activity.
- Every read-model write is a recompute from PostgreSQL, so handlers are idempotent and retry-safe. **Ordering is a property of the write, not of the consumer count:** each recompute carries a `sourceReadAt` token and the write is a Lua compare-and-set that applies only when that instant is newer than the one stored beside the entry. Five clauses make the token usable, because every one of them is a way to get it wrong:
  - It is `clock_timestamp()` taken in the **same statement** as the recompute's `SELECT`, on the primary. Not `now()`: `now()` is `transaction_timestamp()`, so a handler that opened its transaction early and read late would stamp an instant that predates the snapshot it labels, and a handler that opened later but read _earlier_ would carry the newer token and win with the older truth — the exact race the token exists to close. Not a Node clock either: four API replicas do not share one. It is a wall clock, so an NTP step backwards on the primary makes tokens non-monotonic and strands an entry at the future value until the reconciler samples it; a sequence or a snapshot-derived token would not, and is a larger change than this design wants.
  - One token **per batch**, not per scan: a category rescan of 50 000 products runs for minutes, and a single token taken at the top would let a handler that started earlier but read later lose to one that read older truth.
  - The compare-and-set applies when **no token is stored**, and absence must mean _never written_ — so the rebuild's delete is part of its per-product compare-and-set rather than a prefix `UNLINK` in front of it, and a removal leaves the token behind as a tombstone. A prefix `SCAN`+`UNLINK` is then only for ids PostgreSQL no longer has — which means a rebuild has to compute that orphan set, where the old shape needed no difference at all. How it is computed and bounded is the read-model story's to decide and record: holding both id sets in the worker's heap is the 500 000-row memory failure one component over, and an `EXISTS` per id is 500 000 round trips. Where the token and the tombstone live — a hash field beside `updatedAt`, or a sibling key — and what reaps a tombstone under `noeviction` with no TTL are the read-model story's to decide and to record; the obligation stated here is that absence must mean never written. Otherwise a `SCAN`+`UNLINK` rebuild, or clause 5's own removal, takes the token with the entry and a recompute still in flight from before it applies unconditionally over the newer value.
  - It rejects on **equal**. `clock_timestamp()` is microsecond-resolution, so equal tokens do not imply the same snapshot: two recomputes one microsecond apart can differ by a commit only one of them saw, and the loser's value stands until the reconciler's sample finds it. That window is the price of the tie-break, and the reconciler is the backstop; widening the token to break ties is the alternative if a sample ever catches one.
  - The Lua script performs the **whole** read-model write for a product — the hash, both sorted-set scores and any removal — or none of it. It therefore spans three key patterns (`product:{id}`, `category:{c}`, `products:all`), so the all-or-nothing guarantee holds on the single Redis instance this ADR pins and would not survive a move to a cluster. A hash that loses the compare-and-set while its `ZADD` lands would sort a product at the pre-sale score beside its sale price, and the reconciler compares counts and samples hashes, not scores, so nothing would find it.

  It is named `sourceReadAt` rather than `readAt` because the hash already carries an `updatedAt` for display, and two near-synonyms one of which is load-bearing for correctness is the confusion 8c.6 exists to prevent. Four queues means four consumers, three of them read-model writers, so concurrency 1 is no longer available as the serialisation, and a `product.upserted` recompute on a five-thousand-id batch would otherwise land after a flash sale's write and restore the pre-sale price for the length of the sale. No consumer exists yet; the first one to write the read model implements the compare-and-set, and REVIEW.md 3.9 makes a consumer that writes without it a finding.

- The read model is eventually consistent: a write is visible after the handler runs, typically well under a second for single products and a few seconds for a 50 000-product category.
- Redis is a hard runtime dependency; an empty read model answers `503` until the cold-start rebuild completes.
- Ingestion pricing rules are `pricing_rules` rows seeded by migration `0001`, not a TypeScript constant, so they change without a deploy. The seed speaks the vocabulary the ingestion wrapper compiles (`adjustPercentBps` with a signed basis-point `value`, facts from the parsed vendor row); a rule the wrapper cannot parse stops the job rather than mispricing a row, so both sides are pinned to the same rule shapes: an integration test asserts the seeded rows rule by rule, and the pricing module compiles those same seeded rows and prices the case-study row through them. The `type` column separates them from the promotion-layer rules the resolver loads (ADR-0004), and `pricing_rules_active_idx (type, priority desc) where active` serves both loaders.
- Emission after commit is a rule carried by review, not by code. A runtime guard existed briefly, an `AsyncLocalStorage` scope in which the enqueue helpers threw, and it was deleted: nothing ever entered the scope, so the assertion could not fire on any input, and a guard that cannot fire is worse than none because the next reader trusts it. It returns with its first real caller, the database module's `transaction()` helper wrapping its own body.
- Event payloads are validated on both sides of the boundary against the same schemas. The producer parses before the job is added, so a malformed job fails in the request that created it instead of in a worker three retries later; the consumer parses on receipt, because a delayed job can predate the schema the worker now holds. Only the producer half exists today, and the consumer half is the contract the event-handler work has to honour.
- Correlation-id transport across the queue boundary is undecided: payloads are strict, so an id has to be added to the event schemas, and that decision belongs with the work that introduces the logger.
- The queue's logical database comes from `REDIS_QUEUE_DB` through `config.ts`, passed into `EventQueue.connect`. It was a `QUEUE_DB = 1` constant until this branch, which made the configuration's own refusal to let the queue and the read model share a database unable to fire: it validated a value nothing read.
- **A delayed boundary job fires on the producer's clock, not PostgreSQL's.** `PromotionScheduler.schedule` computes its delay from the two timestamps it is given, which its caller must take from PostgreSQL, but BullMQ counts that delay from the producer's own `Date.now()`. An API process running ahead of the database fires `expire` early, the handler reads `active_promotions` on the database clock, still finds the promotion live, and republishes the discounted price; nothing re-fires. The reconciler's boundary sweep is what closes it, which is why the sweep is the mechanism of record rather than the job.
- **A name says whether it is a fact or a piece of work.** A fact is `<entity>.<past participle>` and describes something that already happened, so a consumer may ignore it: `promotion.changed`, `product.upserted`. A job is `<thing>.<verb>` and asks for work, so someone has to do it: `chunk.process`, `readmodel.rebuild`, `reconciler.run`. One queue carries both and BullMQ does not distinguish them, which is exactly why the name has to — a handler that treats a job as a notification drops work, and nothing fails. The delayed boundary work is not a sixth name: `PromotionScheduler` publishes it as `promotion.changed` with a job id per boundary (`promo:<id>:activate`), so `activate` and `expire` are job ids rather than event names.

- **Queues are partitioned by urgency, and nothing is prioritised inside a queue.** Four of them: `promotions` (`promotion.changed` and the delayed boundary jobs), `catalog` (`product.upserted`), `ingestion` (`chunk.process`) and `maintenance` (`readmodel.rebuild`, `reconciler.run`). Routing stays a name-keyed map, `eventRouting`, so a producer cannot choose a queue and an event's urgency is a property of the event rather than of the caller. The partition was two queues until an architecture round showed the split did not isolate what it claimed: `product.upserted` shared the `events` queue with `promotion.changed`, so a 500 000-row import's ~500 announcements queued in front of a flash sale on a `concurrency: 1` consumer — roughly three minutes of backlog before the sale's own rescan started, and each scenario passed alone, so no test saw it. A per-publish queue argument and a job priority were both rejected: the first makes urgency the caller's to remember, the second leaves the two workloads sharing one consumer's throughput. One BullMQ `Worker` per queue, in the same process where that is convenient; separate workers, not separate containers, is the requirement.
- **It is an event queue, not pub/sub.** A job is taken by one consumer and survives until it is; delivery is at-least-once, so every handler recomputes from PostgreSQL rather than applying a delta it was handed. The class is `EventQueue` for that reason: "bus" would promise fan-out this does not do.
- **The partition isolates admission, not consumers, and two workloads still share one.** A category-target `promotion.changed` keyset-scans 50 000 products inline, so `promotions` — the urgent queue — holds the system's longest job, and a cancel racing a mistaken sale waits behind that sale's full rescan. The resolver's answer is to enqueue per-batch `product.upserted` rather than scan inline, which moves the work to `catalog` where it queues behind an import instead; that is the trade, and it belongs to the read-model story. Separately, `readmodel.rebuild` (a 500 000-product recompute, with `SCAN`+`UNLINK` only for the ids PostgreSQL no longer has) shares `maintenance` with `reconciler.run` at one Worker per queue, so the reconciler does not run for the length of a full rebuild — no boundary sweep and no orphan-chunk sweep, precisely when the system is least healthy. The missed ticks are **not** replayed afterwards: BullMQ's scheduler keeps one delayed iteration outstanding, so they are dropped rather than queued. Of the three sweeps, only the boundary sweep **needs** a watermark, and it has one: `reconciler_state.last_boundary_sweep_at` lets the next run cover the whole gap, and without it those re-emissions would be lost outright. The other two re-derive from state — the orphan sweep from every `running` job's `pending` or expired-lease chunks, the drift check from a count comparison — so a missed run costs latency, not work. What an operator sees during a long rebuild is a file stopped at a chunk with no error and no progress, recovering on the first sweep after the rebuild ends, rather than something needing a manual re-enqueue. Either `reconciler.run` takes a fifth queue or the maintenance consumer states its concurrency; the operability story owns the choice.
- `EventQueue.inspect` returns a queue narrowed to three reads. Anything that writes stays off it: `add` would skip both the payload parse and the 2 s bound, which are the two guarantees `publish` exists to give.

### Trade-offs

- Eventual consistency instead of read-your-writes on the storefront. Accepted because the storefront is a catalogue, not a checkout.
- Two stores and a queue to operate instead of one database. Accepted because the case grades the structural answer to flash-sale load, and the safety net (ADR-0007) covers drift.
- Event schemas evolve additively and optionally while a delayed job can be in flight, and that window is the longest promotion window, because a promotion boundary is a delayed job. A payload written before a required field was added fails its `strictObject` parse on consumption, burns its three attempts and lands in the dead-letter set: safe, since the reconciler's boundary sweep still expires the promotion, but silent, since nothing says why. That safety depends on the consumer parsing, which no code does yet, so until the handler lands the real outcome is a handler reading an absent field. Recorded here rather than tracked separately.
- Queue operations are bounded at 2 s rather than left to ioredis, which reconnects for ever while BullMQ's `add` waits on it. An unreachable Redis therefore fails the admin request after its PostgreSQL commit instead of hanging it. The bound is a race that cancels nothing, so a timed-out operation may still land: it buys a fast failure, not a known outcome, and the reconciler reconciles either way — except after a cancel, which the boundary sweep specified in section 9 of the domain design need not catch: it re-emits for `starts_at`/`ends_at` in the watermark window, and a cancelled promotion need have neither in it, in which case the stale hash waits for the sampled price check instead, one reconciler period plus sampling. Sweeping `cancelled_at` in the same window, which section 9 now asks for, is the reconciler pull request's job. Closing the queues does not drain in-flight operations either, so shutdown stops producers first and bounds the wait: `SHUTDOWN_DRAIN_TIMEOUT_MS` (10 s, through `config.ts` like every other variable) caps how long `server.close` may wait for open connections before the queues are closed and the exit is taken anyway, because one long request would otherwise hold the process until the orchestrator sends `SIGKILL`. The forced path is the enqueue-after-commit window under another name: a request that commits just before the cap has its publish torn out from under it, leaving the read model stale until the reconciler's sweep, exactly as a crash between the commit and the enqueue would. Connecting has its own budget, `EventQueue.CONNECT_TIMEOUT_MS` (10 s, a constant rather than an environment variable), because a managed `rediss://` instance pays DNS and a TLS handshake once and 2 s is not generous for that, while 2 s is the right bound for an operation on a connection that is already open. A queue-unavailable failure is not yet distinguishable from any other 5xx by a metric; that arrives with the logging and metrics story. The alternative, giving up reconnection so the command fails on its own, would leave a long-lived producer permanently disconnected after one blip.
- Emission after commit without a transactional outbox: a crash between commit and enqueue leaves stale entries until the reconciler repairs them within five minutes.
- Migration `0000` is edited in place and regenerated whenever the schema changes, because nothing is deployed yet. `__drizzle_migrations` does **not** key on the file hash, which an earlier draft of this record claimed: the hash is stored and never read. The migrator takes the single most recently applied row (`order by created_at desc limit 1`) and applies every journal entry whose `when` timestamp is greater (`drizzle-orm/pg-core/dialect.js`). Two consequences. A database that already ran an older `0000` keeps the older shape for ever, so the forward-only rule (REVIEW.md 11.1) starts at the first deploy. And a migration merged out of order — branch B generates `0004` at a timestamp earlier than branch A's `0003`, A merges first — is silently skipped on every database that has already applied A, for ever, while the boot reports success. Two entries in this journal are 9.5 seconds apart, so parallel worktrees make that an ordinary afternoon rather than a corner. The guard is in two halves, because one file cannot answer the whole question. `tests/unit/shared/db/migration-journal.test.ts` asserts what the file knows: timestamps increasing with the index, never repeated. The half that matters on merge is a `ci` step comparing the journal against the pull request's base, since an entry sorted into the middle leaves the file looking perfectly ordered and is skipped only on databases that already passed its timestamp. The integration count assertion is the weakest of the three and cannot fail while the journal is ordered.
- Drizzle cannot express `exclude using gist`, so the two promotion exclusion constraints and the `btree_gist` extension exist only as hand-written SQL in migration `0000` and are invisible to the modules' `db/schema/` directories. Accepted because the database must own the conflict rule (ADR-0004); the cost is that a regenerated migration will not reproduce them, so schema and migrations are kept in step by hand and asserted by the integration tests (REVIEW.md 11.4).
- Connection budget: `createPool` fixes `max: 10` with a 10 s `statement_timeout` and a 10 s `idle_in_transaction_session_timeout`. Four process types against a default `max_connections` of 100 leaves room for about nine processes, so `--scale ingestion-worker=8` is the ceiling before the pool size has to come from the environment.
- Schema drift is a CI step rather than a convention, and it is four commands rather than two: `npm run db:generate < /dev/null` teed to a log, `grep -qE 'No schema changes|Your SQL migration file'` over that log, `git add -AN src/shared/db/migrations`, then `git diff --exit-code src/shared/db/migrations`. It fails the build when a module's `db/schema/` was edited without regenerating. That is the direction it catches. The opposite one — a regeneration that drops the four hand-written objects — it cannot catch, because a committed regeneration leaves a clean tree; the integration tests are what notices that, which is why they assert each of the four directly. The tool's own success line is what is asserted, and its exit status is not, because **`drizzle-kit generate` exits 0 when it fails.** Measured on the pinned 0.31.10 against a renamed column: it needs an interactive answer, cannot get one because CI has no TTY, prints `Error: Interactive prompts require a TTY terminal`, writes no migration — and exits 0. An unresolvable import and a bad path do the same. A step that trusted the exit code then has nothing to diff and passes green over exactly the drift it exists to catch, which is what this step did before the assertion was added; the fix is verified in both directions, the assertion failing against the renamed column and passing on a clean tree. `< /dev/null` is not what keeps the job from hanging to the 15-minute timeout — CI has no TTY to prompt on in the first place — it is for the developer running the same command locally, where a TTY does exist and the prompt would otherwise wait for a person. And `git diff` cannot see an untracked new migration file, so without `git add -AN` the check would rest on drizzle-kit also appending to the tracked `_journal.json` rather than on the migration itself. The step needs no database; `generate` reads the schema files and the snapshots. The cost of asserting on output is that the contract is a human-readable line from a tool the lockfile pins at 0.31.10. It fails closed — any wording drizzle-kit stops printing turns the step red, never green — but a dependency bump that renames those lines is a red build whoever raises the bump has to recognise as theirs.
- Migrations run on their own single-connection pool with both timeouts set to `0`, because a migration killed halfway leaves `__drizzle_migrations` unwritten and every retry replays the same statement. The test harness and `src/shared/db/migrate.ts` both do this, and deliberately do not share `createPool`, whose 10 s `statement_timeout` would kill a long index build at the same second on every boot. `npm run db:migrate` on the host still goes through `drizzle-kit`, which reads `drizzle.config.ts` and sets neither timeout, so a managed PostgreSQL with a server-side `idle_in_transaction_session_timeout` needs it lifted for that path. `CREATE INDEX CONCURRENTLY` cannot run inside the transactional migrator at all, so a hot-table index (REVIEW.md 11.2) will need a migration applied outside it.
- `ingestion_jobs.chunks_done`, `rows_processed` and `rows_rejected` are one hot row per job that every chunk worker updates: one update per completed chunk, so tens to low hundreds per file at the 4 MiB chunk size of ADR-0005, spread over minutes. That serialises the workers for the length of one update and is accepted rather than aggregated out of `ingestion_chunks`, because the job-status endpoint then costs one row read instead of a scan (REVIEW.md 6.20).
- A weekly 500 000-row upsert leaves as many dead tuples across `products` and its two indexes. Autovacuum defaults (20 % scale factor) trigger well inside one week at this table size, so they are left alone; the ingestion PR re-checks the assumption against the real row count before it ships (REVIEW.md 6.17).
- `products.updated_at` defaults to `now()` and has no trigger; the writer sets it so the `is distinct from` guard can skip unchanged rows and a weekly upsert does not rewrite 500 000 of them. The cost is that the value comes from the application clock, not the database's, so `products.updated_at` is not a watermark any sweep may filter on — `pricing_rules.updated_at`, which a server-side trigger sets from `now()`, is.
- **The exclusion constraints span all time, not "active now".** `tstzrange(starts_at, ends_at) WITH &&` under `WHERE status = 'active'` conflicts a new promotion with any overlapping active one on the same target, a promotion whose window closed a week ago included. The operator-facing symptom is a `409` naming a promotion that has already ended. Accepted because folding `now()` into the index predicate is not possible — an index predicate must be immutable — so the cure is cancelling the corpse, and ADR-0006's boundary jobs are what stop them accumulating.
- **Extending or deepening a live promotion therefore has to be one guarded `UPDATE`, never cancel-then-create.** An exclusion constraint does not conflict a row with itself, so `UPDATE promotions SET ends_at = $2, value = $3 WHERE id = $1 AND status = 'active' AND ends_at > now()` changes a running sale with no gap. As two mutations it would publish base prices to every product in the category between the calls: for a category sale, two 50 000-row rescans and a visible price blink for a single price edit. No such route exists today — ADR-0004 and the design spec's section 10 carry three promotion mutations (create, assign, cancel) and no edit — so this records the shape that permits an edit, not a decision to add one.
- **`now()` is `transaction_timestamp()`, so promotion liveness is frozen for the length of a transaction.** That is precisely what lets the boundary test assert an instant (`tests/integration/shared/db/active-promotions.test.ts`), and it is a hazard everywhere else: a worker wrapping several chunk batches in one transaction would price every batch against the transaction's start rather than the wall clock. `statement_timeout` bounds a statement, not a transaction, so nothing else bounds it. Batch loops commit per batch.
- The image installs with `npm ci --ignore-scripts` in both stages, because the only lifecycle script here is husky's `prepare`, which has no `.git` to install into and fails the build. The runtime stage installs again with `--omit=dev`, so `drizzle-kit` and its platform-specific `esbuild` binary never enter the image; the migrator that does ship is `drizzle-orm`'s, already a runtime dependency. This replaces the `migrate` one-shot, which reinstalled 513 packages inside its container on every invocation (measured 9.5 s and 9.3 s) because `--rm` discarded the anonymous `node_modules` volume with the container.
- Four SQL objects are hand-written into the migrations and have no expression in any module's `db/schema/`: the `btree_gist` extension, the two promotion exclusion constraints, the `pricing_rules_set_updated_at` trigger with its function, and the `reconciler_state` seed row. `npm run db:generate` cannot reproduce them, so a regeneration drops all four, and the CI drift step above does not catch that direction — the integration tests, which assert each of the four directly, are what notices. The `active_promotions` view is not a fifth: `drizzle-kit` generated migration `0002` from the `pgView` in `src/modules/promotion/db/schema/active-promotions.ts`, so it is inside what a regeneration emits rather than outside it, and `npm run db:generate` reports no changes on a clean tree.

### Rejected alternatives

- Single PostgreSQL with computed effective price and a versioned Redis cache: simpler, but the sort by effective price cannot use an index and every cache miss during a flash sale is a top-N sort over the category; rejected once the read-model approach was costed.
- Prisma: heavier runtime and generated client; Drizzle keeps SQL visible, which matters for the exclusion constraints and keyset scans.
- Kafka or a hosted queue: more moving parts than a case study warrants; BullMQ reuses Redis and offers delayed jobs, retries and a dead-letter set out of the box.
- An in-process command/query bus (Nest's CQRS recipe, MediatR): those buses dispatch in memory inside one process and ship no read store, so they address the axis this decision does not need and leave the one it does untouched. Express's router and middleware already collect the handlers and run the cross-cutting work, and a second dispatcher earns its keep only when one command has more than one entry point.
- Event sourcing with an `AggregateRoot` and `apply()`: events here are notifications rather than the source of truth, and every read-model entry is recomputable from PostgreSQL. That recomputability is what lets the reconciler exist and what makes an at-least-once queue acceptable rather than dangerous.

## ADR-0004: Promotion resolution and effective price

**Status:** Accepted

### Context

Promotions target either one product or a whole category, have a validity window, and the business rule says a product has at most one active promotion. The rule must hold under concurrent admin writes, and a product created inside a promoted category must inherit the discount automatically.

### Decision

Promotions are rows, not rules: `discount_type` of `percentage` or `fixed`, `value` in basis points or minor units, `starts_at`, `ends_at`, exactly one of `product_id` or `category` once active, and a `status` of `draft`, `active` or `cancelled` (a draft has no target; a cancelled row keeps the shape it had). The enum is the case's own vocabulary, and a third kind of discount is a migration that widens it — the right cost, because a vocabulary a reader can enumerate is worth more than one that can hold anything. Two PostgreSQL exclusion constraints (`btree_gist`, `tstzrange(starts_at, ends_at) &&`) guarantee at most one active product-level promotion per product and at most one active category-level promotion per category at any instant. Overlap at the same level fails with a `409` that names no promotion; there is no silent override. That `409` is SQLSTATE `23P01` raised by the constraints, never a check-then-insert: `PromotionRepository.insert` and `.assign` catch the violation and return `{ ok: false, reason: 'overlap' }`, which the commands turn into a status. No second query runs: the envelope carries no `details` (ADR-0009), so there is nowhere to report a conflicting row and nothing fetches one.

Which candidate applies is decided by `json-rules-engine` rules stored in `pricing_rules` (`type = 'promotion'`) and cached for 60 seconds, not by hard-coded precedence (owner decision, 2026-09-12). The resolver computes each candidate's discount first, then hands the engine a single fact object holding both candidates, so a rule can compare them; the highest-priority rule that fires names the winning level, an equal price decided by the `<=` in the seeded `lower-price-product` rule rather than by a tiebreak in code — the exclusion constraints already guarantee one candidate per level, so a resolver-side id tiebreak would be a branch no test could reach; the seeded default rule gives the customer the lower of the two effective prices, so a category flash sale covers a product that carries its own promotion rather than skipping it. A higher-priority rule overrides that default by naming the other candidate, which is how a deliberately set product price survives a category sale; it cannot select nothing, so a product with no promotion of its own cannot be held out of one without a `level: 'none'` the event vocabulary does not have. Changing the policy remains a row edit rather than a deploy.

**The rule decides which candidate wins; it does not decide how one is computed.** A matching rule's event names the winner and nothing else: `{ type: 'selectCandidate', params: { level: 'product' | 'category' } }`. The arithmetic is pure and sits behind one entry point over a typed row — `EffectivePriceCalculator.calculate(basePriceCents, promotion)` in `src/modules/promotion/domain/`, returning a `PricingOutcome` discriminated union of `{ ok: true, effectivePriceCents }` or `{ ok: false, reason }`, so a failure carries no price a caller could publish by mistake. Each discount type owns its formula and its own value check in a file of its own — `percentage-discount.ts` and `fixed-discount.ts`, each implementing the two-method `Discount` interface — and `EffectivePriceCalculator` looks one up rather than branching on the type (owner decision, 2026-09-12). The injected `discounts` is a `Record<DiscountType, Discount>` keyed by the union itself, so widening the union does not compile until its calculator exists: a discount type cannot ship half-wired, and the 10 000 basis-point ceiling moved into the percentage calculator instead of sitting in a guard that had to know what percentage means.

**Exhaustive over the union is not exhaustive over the database.** The PostgreSQL enum and the TypeScript union are two vocabularies that can skew by a deploy, so the lookup is an own-property check inside `calculate`, returning `Discount | undefined`; `EffectivePriceCalculator` turns `undefined` into `{ ok: false, reason: 'unknown discount type' }`. Indexing the map directly would have called `valueError` on `undefined` for a row carrying a type the union does not have yet — the handler throws, retries and stops repricing that product — and a `discountType` of `toString` would have reached a prototype function on the way to the same crash. The map is a private field, and the discount is resolved once and handed to the guard, so no caller reaches the arithmetic unguarded. This is a closed lookup, not the registry the owner reversed on 2026-09-12: that one was runtime-pluggable — a calculator named on the promotion row with a parameter bag beside it, shared with `src/modules/pricing/` — where this one is a fixed two-member map with a rejecting boundary in front of it. Adding a discount type is still a migration that widens the enum plus a file and one line in the map, never a row an operator can write; a row that arrives before the code does is priced by nobody rather than crashing the worker. Dynamic pricing rules for ingestion live in `src/modules/pricing/` with their own adjustment semantics, and neither module imports the other.

The rule "at most one active promotion per product" is implemented as **at most one applied promotion**: whichever candidate prices the product lower under the seeded rule, or whichever a higher-priority rule names, and none if no rule fires. Each formula is written once and in one place (REVIEW.md 1.3): percentage is `base - floor(base * bps / 10000)` in `percentage-discount.ts`, fixed is `max(base - value, 0)` in `fixed-discount.ts` with the clamp in `EffectivePriceCalculator.calculate`, computed in `bigint` and clamped into `[0, base]`. `EffectivePriceCalculator.calculate` remains the only entry point; the guard receives the discount it has already resolved, and nothing outside the domain imports a calculator directly. Three mutations exist: create (with a target → `active`, or without → `draft`), assign (`draft` → `active`, target set in the same guarded `UPDATE`, which rejects with a `409` carrying its own message — a different sentence from the overlap `409`, the status being the whole taxonomy (ADR-0009) — when the row is not a draft, when a concurrent assign won, or when its `ends_at` has already passed, and runs the exclusion constraints in the same statement) and cancel. A draft is never applied. Whether a promotion is active is decided on PostgreSQL's clock and nowhere else (REVIEW.md 2.7), with one boundary-only exception: `create-promotion-input.ts` rejects an `endsAt` already in the past against the API's clock, before any row exists. Drift there moves that rejection by the drift, so a window ending within the drift can be stored and immediately report `state: 'expired'`. Everything that decides whether a stored row is running is SQL: an `active_promotions` view whose predicate on `now()` gates the candidates, selected from rather than re-derived, so no TypeScript predicate exists for a Node clock to drift against (owner ruling, 2026-09-13). The view is `src/shared/db/migrations/0002_active_promotions.sql`; no TypeScript predicate remains. Read endpoints for promotions serve the admin path from PostgreSQL directly, because `GET /api/promotions` and `GET /api/promotions/:id` must show drafts, scheduled and expired rows, which the view by definition does not hold. They project a five-valued `state` — `draft`, `scheduled`, `live`, `expired`, `cancelled` — from one SQL `case` over `now()` (one `sql` fragment in `src/modules/promotion/db/promotion-repository.ts`), used by every promotion read **and** by every write's `returning` clause, so a create, an assign and a cancel report the state a later read would. Nothing in TypeScript derives it — `PromotionState` is a type with no constructor — and no filter accepts `state` as a query parameter, because that would be a time predicate composed by a caller. Boundaries are scheduled with delayed BullMQ jobs, enqueued at the moment a promotion first becomes active (create-with-target or assign), so an assigned draft reaches the read model immediately: `expire` at `ends_at` always, `activate` at `starts_at` only when the window has not already opened. A promotion that is live the moment it becomes active needs no activation job — the announcement that accompanies the write is the activation, and scheduling one anyway would give it `delay: 0` and rescan the same category twice (`PromotionAnnouncer.announce`).

**One event name, not five.** Create-with-target, assign, cancel and both scheduled boundaries all enqueue `promotion.changed` carrying `{ promotionId }` and nothing else (`src/modules/promotion/domain/promotion-announcer.ts`). The read-model handler recomputes the affected products and never asks why the promotion changed, so five names would be five handlers with one body, and one name is what lets the reconciler re-emit a missed boundary idempotently. The enqueue happens after the row has committed and its failure is logged and swallowed: the write stands, which is a smaller failure than telling an admin their write did not happen. **What repairs it is weaker than "the reconciler" suggests**: ADR-0007's boundary sweep is keyed on boundaries crossed since a watermark, and a create or assign whose start has already passed crossed before it, so only the sampled price check finds it — near-certain on the first run for a category promotion, and a repeated 1 % sample for a product-level one. None of it exists in the repository yet. Cancel announces before it removes the delayed boundary jobs, and each step is settled on its own: the event is the correctness half, so it cannot sit behind a queue call that may time out. Removing the jobs is hygiene: a boundary job carries only `{ promotionId }`, and its handler re-reads the row, finds it cancelled and publishes the base price.

### Consequences

- Concurrency is solved in the database: two admins assigning to the same product at once get one `201` and one `409`, with no application-side locking.
- Under the seeded default a category flash sale covers products that carry their own active promotion rather than skipping them, because the lower price wins. The applied promotion is returned in every storefront response, so an admin can see which candidate won. A product that must not be discounted further is expressed as a higher-priority rule, not as code.
- The retired shape is unconstructible in the application and unstorable in the database. `src/modules/promotion/domain/dto/discount-type.ts` declares `DiscountType` as `percentage | fixed` and `dto/promotion.ts` a `Promotion` interface carrying `discountType`, `value`, `status`, `startsAt` and `endsAt` — no `calculator` field and no parameter bag to put one in, so a promotion naming a calculator does not typecheck. The `discounts` map is keyed by that union, and the calculator's lookup rejects anything outside it, so a calculator name arriving in a row selects nothing rather than something. `src/shared/db/migrations/0000_write_store.sql` went back to a `promotion_discount_type` enum plus `value integer`, with `check (value > 0)` and the 10 000 basis-point ceiling, so there is no `calculator text` or `params jsonb` column left for such a row to sit in. Both halves are on `main`, so the claim is about the schema as it stands.
- Categories are free text matched exactly, and a category promotion whose category matches no product is accepted, because products arrive later through ingestion. **A mistyped category is therefore invisible at the API**: the write answers `201`, the sale covers nothing, and nobody learns until the storefront is read. The design once carried a `productCount` on the response to make it visible; it was never built, and reporting a count that ingestion can change a second later would have been a number nobody could act on.
- A separate `assign` step exists because the case lists create, cancel and assign as distinct operations; keeping the target on the promotion row (one target per promotion) makes assign a single constrained `UPDATE` rather than a join table.
- Cancelled promotions stay in the table for audit; the partial `WHERE` on the constraints ignores them, so cancel-then-create works.
- Cancel is idempotent: a second call answers `200` with the already-cancelled row rather than a conflict, and `cancelled_at` keeps the first cancellation's instant, because the `UPDATE` is guarded by `status <> 'cancelled'` (`PromotionRepository.cancel`). It announces only when that guarded `UPDATE` matched a row, so a repeat call does not fan the recompute out over the category a second time.
- The admin list pages by keyset, not by offset: `after` is the last `id` of the previous page and `limit` bounds it (default 50, maximum 100), ordered by `id`. `id` never changes, so a promotion created mid-read cannot make a page repeat or skip a row, which an `OFFSET` would. The response is `{ items }` with no cursor of its own — the caller reads the last id it received — and a short page is the end of the list.
- Scheduled starts and expiries change prices at the boundary, not on a cache TTL.
- Cancel can see the race it lost: `PromotionScheduler.cancel` returns BullMQ's removal code per boundary, where `0` means a worker already holds that job and `1` means nothing blocked the removal, including when there was no such job. The caller can log the `0`. The end state is correct as long as the cancel endpoint also publishes an immediate `promotion.changed`: both recomputes read the current truth, and the compare-and-set above decides which write survives if they race. The scheduler removes only, so that publish is a contract the cancel endpoint has to honour rather than something the scheduler enforces.
- The boundary delay is computed from an injected clock rather than `new Date()`, so the caller decides. It must pass PostgreSQL's `now()`: on application clock drift an activate fires before its window opens, the handler finds the promotion not yet active, and the base price stands until the reconciler's boundary sweep corrects it (REVIEW.md 1.6, 1.7).

- **No test pins the runtime policy, and that is what makes "the policy is data" true rather than decorative.** A test asserting whichever row a running database holds would make it unchangeable without turning CI red, and a policy that cannot change is not data. Tests assert the mechanism instead — given a rule row the test itself inserts, the engine selects that candidate. Two things that look alike are not: a test that reads the **seeded** rules out of the migrated database tests code — the seed is a migration row, reviewed and changed by commit, and changing it changes the test with it, as with any code. A test that pinned the **runtime** row would be something else entirely: an operator editing that row in a running database changes neither code nor test, so CI stays green and the policy really is data. Both halves have to be said, or the rule reads as forbidding the first.
- The **promotion** rule seed (not migration `0001`'s three ingestion rules) is **four** rules, not three: a `json-rules-engine` rule carries one event, and "the lower price wins" is two outcomes. One rule comparing the candidates could name only one level, and the other comparison would fire nothing — publishing a base price in the middle of the sale. A reader counting the rules should not conclude one is missing.
- Priorities 10–30 are reserved for the seeded rules; an operator override sits above 30, or it is shadowed by `product-only` for the arity-one products that rule also names, and the same intent then behaves differently depending on whether a category sale happens to be running.
- **The rule set is cached for 60 seconds and nothing invalidates it.** After a policy edit, workers hold two policies for up to a minute, and thereafter only products that receive an event are re-resolved directly. The reconciler's sampled sweep heals the rest, comparing a sample per category against PostgreSQL and enqueueing a rebuild on a mismatch, so the exposure is probabilistic across several runs rather than indefinite — a weaker guarantee than it sounds, which is why it is recorded rather than left to be discovered. Closing it properly needs a version to compare against (`pricing_rules.updated_at` is the obvious carrier; there is no version column today) and a write path to hang a trigger on (section 10 has no `pricing_rules` endpoint). Neither is built here.
- **`products.pricing_rules_version` cannot see a deletion.** It stores the rule set's `max(updated_at)` in epoch milliseconds, so an operator deleting a rule leaves the version unchanged and two rows stamped with the same value may have been priced by different rule sets. Deleting the row that _held_ the maximum is worse than unchanged: the version moves **backwards**, so a sweep repricing everything below the current version repairs the rows that were already correct and skips the stale ones. A rule is therefore retired by setting `active = false`, never by `DELETE` — the `BEFORE UPDATE` trigger bumps `updated_at`, `pricing_rules_active_idx` already filters on `active`, and the version stays monotonic. That monotonicity is discipline, not a constraint: nothing in the schema stops `DELETE FROM pricing_rules`, and nothing can while the only writer is a person at a psql prompt. Enforcement — a soft-delete-only grant, or a rule forbidding the statement — lands with the write path that first adds one, because there is no endpoint to hang it on here. The same applies to ordering: the trigger sets `updated_at` from `now()`, which is `transaction_timestamp()`, so `max(updated_at)` orders by when a transaction started rather than when it committed. With one human writer that is exact; the moment two overlapping writers exist, the later-committing one can stamp a version below one already observed and reopen the skip-the-stale-rows window by a second route. It identifies the newest edit, not the rule set; a hash over the active rows would identify the set, and is not built here.
- **The promotion policy is empty until its rules are seeded.** Migration `0001` seeds `type = 'ingestion'` rules only; the promotion rules are not written yet. Until then no promotion rule fires for any product, so `promotion_rules_no_event_total` counts every product carrying an active promotion. That is the counter working, not a regression, and any alert on it is expected to be red for that interval.

### Trade-offs

- Precedence lives in data, so a wrong or missing rule changes prices without a code review. The mitigation is that the seeded default ships in a migration and is version-controlled, every later change is an ordinary row update that the table's `updated_at` records, and a rule naming an unknown candidate is ignored and logged rather than applied. Changing the policy therefore needs no deploy, which is the point, and `updated_at` records only when the current policy arrived, not what preceded it, and no published price names the rule that selected it — so this is a weaker audit trail than the git history it replaces, not a stronger one.
- `json-rules-engine` returns **every** matching event, not the first, and does not stop at a success. The resolver therefore selects the event whose rule carries the highest `priority` in `results` rather than reading `results[0]`: buckets run in descending priority but rules inside a bucket run concurrently, so positional order is an implementation detail the library does not promise across versions. Distinct priorities are a seed contract rather than a convention, and a collision is logged at load.
- Protecting a deliberately set product price inside a category sale means writing an operator rule above priority 30, so the protection is itself an un-reviewed row, carrying the same absent audit trail as the policy it overrides.
- Which campaign is credited moves with `base_price_cents`: a product-level fixed discount and a category percentage can swap places when a vendor feed changes the base price, with no admin action and no promotion mutation. Product-level precedence was stable under base-price changes; the lower price is not, so the storefront naming the applied promotion is what keeps this auditable.
- Deleting the activity guard rather than repointing it at the database clock is a decision, not a cleanup (owner, 2026-09-13): the application can no longer ask whether a promotion row it already holds is active, so anything that needs to know re-reads through the gating query and a caller holding a stale row has no local way to detect it. The boundary tests that pinned `starts_at <= now() < ends_at` in TypeScript went with it, and that predicate is now covered only where it runs, in SQL — by `tests/integration/shared/db/active-promotions.test.ts` against a real PostgreSQL. Acceptable because one predicate on one clock is the point of REVIEW.md 2.7: a second implementation that agrees except at the boundary is worse than none, and the boundary is exactly where ADR-0006's delayed jobs are supposed to make the price crisp.
- The engine adds a per-resolution evaluation over at most two candidates. That cost lands on the event handler and the reconciler, never on a storefront read, because the read model stores the already-resolved price.
- Cross-level coexistence is allowed rather than rejected. Rejecting it would require an application-side check that races; allowing it keeps the database the sole arbiter.
- Two discount types cost three files (the `Discount` interface and one calculator each), plus the map and its lookup inside `EffectivePriceCalculator`, instead of one ternary, and a reader wanting both formulas side by side now opens two files instead of one line. Acceptable because the cost is paid once and it moves the third-type check from a reviewer to `tsc`: the failure it prevents is a new enum member falling through a branch to the wrong formula, which is a wrong price on a live storefront rather than a red build. It also stops the pricing function from knowing what percentage means — the basis-point ceiling is the percentage calculator's business, not the guard's.
- The unknown-type branch is unreachable in TypeScript and is tested through a cast. A branch the types say cannot happen is a cost — it is one more path to keep covered at 100 % — and it is paid deliberately, because the types describe one deploy and the rows come from another. The residual behaviour is still a gap rather than a fix: a promotion with an unrecognised type is priced by nobody, so the product publishes its base price and the failure is visible only in the defect log until the code catches up with the enum.
- Percentage discounts round in the customer's disfavour by at most one cent (floor on the discount). Stated, deterministic, testable.
- Only the ingestion rules are seeded (migration `0001`). Until the promotion rules land, `pricing_rules` holds no `type = 'promotion'` row, so the resolver has nothing to fire and no promotion is applied; the schema is ready before the policy is.
- The `discount_type` enum buys an enumerable vocabulary at the price of a migration for every new kind of discount (Decision). Acceptable for ModaCo: percentage and fixed are the case's own two, and a third is a deliberate product decision, not a configuration change.
- "Active" is expressed three times — the `active_promotions` view (live at `now()`), the exclusion constraints (overlapping at any instant) and the `state` fragment in `PromotionRepository` (which of five states a row is in). Three predicates instead of one is the cost of each answering the question it is actually asked: the resolver wants the running promotion, the constraints must reject a future overlap the view does not hold, and the admin list must show the rows that are not running. They are kept from drifting by the half-open `tstzrange` boundary they share, by the integration test that fails if the view's bound changes (an integration test pins the boundary), and by all three living in SQL on one clock — a fourth copy in TypeScript is what REVIEW.md 2.7 forbids, not a second SQL expression.
- The overlap `409` names no promotion, so an admin refused one finds the blocker with `GET /api/promotions` filtered by `productId` or `category`. Acceptable because the exclusion constraints are keyed on exactly those two columns, so that filter is one the admin already has; what is given up is the one-request answer.

### Rejected alternatives

- `product_promotions(product_id unique)` join table: not time-aware (blocks scheduling a future promotion), does not cover category promotions, and materialising category assignments means 50 000 inserts per flash sale.
- Encoding the promotions themselves as `json-rules-engine` rules (rather than the policy that selects between them): that would duplicate the source of truth, since a promotion's type, value, window and target are already structured columns that the constraints and the scheduler operate on. The rules decide precedence; the rows stay the promotions.
- Keeping an application-side activity predicate fed by a `select now()`: rejected because it leaves the predicate written twice in two languages, which is what REVIEW.md 2.7 forbids, and buys only the ability to re-check a row already fetched.
- A calculator named on the promotion row (a `calculator` column plus a `params` bag) resolved through a registry shared with `src/modules/pricing/`: rejected by the owner (2026-09-12) because it leaves the set of discount shapes unbounded and unreviewable, and couples two modules that only look alike. The `Record<DiscountType, Discount>` kept here is the opposite trade — closed, exhaustive, checked by the compiler, private to the promotion domain, with one runtime guard at the point a database row crosses into it.
- Unconditional product-level precedence, where a product's own promotion always beats its category's: rejected by the owner (2026-09-12) in favour of the lower effective price, because it shows a customer a worse price than the category campaign advertises; a deliberately set product price is protected by a higher-priority rule instead.

## ADR-0005: Chunked, leased, checkpointed ingestion (Scenario A)

**Status:** Accepted

### Context

Weekly vendor files of 500 000+ rows must pass through application-layer pricing rules before reaching the database. The processing unit runs on a serverless consumption plan: a strict timeout of minutes, restricted memory, and no state after the invocation ends. The naive design (stream the file inside one HTTP request, enqueue 5 000-row payloads, let the queue retry whole chunks) fails all three: the request itself times out, row payloads fill the queue's Redis, and a retry restarts a chunk from zero.

### Decision

**Pattern:** register once, then process many small, independent, resumable units.

- The API streams the upload to a file store (local volume; blob storage in production, where a pre-signed upload plus a blob trigger replaces the API hop), hashes it, computes line-aligned byte-range chunks (4 MiB default) in one streaming pass, and stores `ingestion_jobs` plus one `ingestion_chunks` row per chunk. Duplicate files (`file_sha256` unique) and a second concurrent job for the same vendor are rejected with `409`.
- Each chunk is a BullMQ job whose payload is just `{ jobId, chunkIndex }`. `processChunk` is the serverless unit: it claims the chunk with a **lease** (`lease_until`), streams its byte range, splits raw buffers on `0x0A`, parses `vendor_price` decimals to integer cents without floating point, dedupes each 1 000-row batch by SKU, runs the rows through `json-rules-engine` rules loaded from `pricing_rules` where `type = 'ingestion'` (the same table also holds the promotion-precedence rules of ADR-0004, cached separately), and commits the multi-row upsert together with a **compare-and-set checkpoint** (`where next_offset = $seen`) in one transaction. It stops when its time budget is spent and re-enqueues itself; the checkpoint is already durable.
- **Tools:** BullMQ (retries, stalled detection sized to the budget, failed set as DLQ), `json-rules-engine` for the dynamic pricing rules, Node streams, PostgreSQL `INSERT ... ON CONFLICT`.
- **Pricing rules** (`src/modules/pricing/domain/`: `base-price-calculator.ts` and `base-price-calculator-cache.ts` are the entry points, one class each, over every shape under `domain/dto/` per REVIEW.md 8c.8 — `pricing-rule-row`, `pricing-outcome`, and the `vendor-row-facts` and `adjustment-event` zod schemas, which are shapes whether or not they carry a validator, one declaration per file per 8c.2, under `domain/` per REVIEW.md 8c.7). Each active `pricing_rules` row of type `ingestion` carries a `json-rules-engine` condition and one adjustment event, `adjustPercentBps` or `adjustCents`. The three case-study rules are rows seeded by migration `0001_seed_pricing_rules.sql`, not a constant in the module (owner decision, 2026-09-12): reference data lives in the database, so the wrapper reads what ingestion will actually apply. An integration test compiles the seeded rows and prices the case-study row through them, because the two sides invented different rule vocabularies once already and neither side's own tests could see it.
- **Order and arithmetic.** Matching rules apply in priority order to the vendor price, ties broken by rule id so the order is total even though `priority` defaults to 0. Every step is computed in `BigInt` and floored, so composing several rules never loses a cent to floating point.
- **Provenance.** `pricing_rules_version` is the maximum `updated_at` of the active ingestion rules in epoch milliseconds, written on every row the run upserts, so a price carries a hint at the rule set that produced it. Its limits are in the trade-offs below.
- **Whose fault a failure is.** A rule whose result falls below zero or above the largest exact cent value rejects that row alone (`fault: 'row'`) and names the rule. A rule set that cannot run at all reports `fault: 'rules'`, so the caller stops the job instead of rejecting 500 000 rows one at a time. That separation covers a rule set that cannot run at all; a rule that runs and rejects every row it sees is still reported one row at a time, which the trade-offs below name. `rejectedBy` carries the same `pricing rule <id> ("<name>")` shape as the compile error, because the engine reports a fired rule by name only, so the id travels inside the name and a rejection names a row a reader can go and look at.
- **What fails at compile time.** A malformed rule throws before any row is priced. `BasePriceCalculator.fromRules` parses the event with zod, which bounds `adjustPercentBps` at -10 000 basis points, the value that already takes the price to zero, so a larger discount is rejected with the rule named rather than rejecting every row it touches. `adjustCents` keeps the full integer range, because a large fixed rebate is legitimate and an impossible one can only be judged against a price. Neither has an upper bound, since no principled maximum markup exists and the largest-exact-cent guard is the backstop. Each rule is then run once against a probe row, so an unknown operator or a fact no vendor row carries fails once instead of rejecting every row of a file while the job still reports success. A condition group with an empty `all` or `any`, at any depth, is rejected in the same pass and before the rule is added, because both are well-formed and both fire on every row — `json-rules-engine` returns true for an empty condition set whatever the operator (7.3.1, `rule.js`, verified by running it), so the empty `any` is not the harmless half it reads as, and nothing later would stop either (trade-offs below). One more defence is in code and belongs here: runs against a shared engine are serialised through a queue, because `json-rules-engine` keeps per-run state on the engine and two overlapping runs clobber each other's results; a run that throws spends the engine rather than leaving it half-used, and the nine-rule overlapping-run test is what holds it. The queue is a field of `BasePriceCalculator`, the one object that holds the compiled engine. Production reaches a calculator only through `fromRules`, which builds its own `Engine`, so two calculators over the same rows are two engines with a queue each and nothing shared to clobber. The constructor is public for tests that need an engine they prepared themselves, and that is the one way to defeat the queue: two calculators over one `Engine`. That placement was found by trying the wrong one first: with the queue on a separate pricer the guarantee quietly became "one pricer per rule set", and four tests went red the moment each call built its own. A caller contract nothing enforces is not a defence. The batch entry point the chunk processor needs stands on the memory measurement alone.
- **What the engine is allowed to see.** The fact surface is exactly `category`, `vendorPriceCents` and `stockQuantity`, the fields a vendor row carries; a seeded rule naming anything else fails to compile, which is why the seed as first written could not run at all. Promotion-layer rows share the table, so `BasePriceCalculator.fromRules` skips anything but `type = 'ingestion'` rather than trusting the loader's query to carry the filter: a promotion rule reaching this engine would fail to parse and kill every ingestion job. Before the engine sees a row, the wrapper parses it against the fact schema, because a fact that is missing or null is not a condition that is false: `json-rules-engine` either throws `UndefinedFactError`, which would stop the job over one bad row, or compares `null` and quietly skips the rule, which writes an under-priced `base_price_cents` with no trace in the result. Both are one rejected row naming the offending field. A category is trimmed before it is matched, since a padded field is the same category and comparing it untrimmed would price the row as though it belonged to another one; nothing but spaces is unusable and rejected. The trimmed value is also what the ingestion upsert writes to `products.category`, so the string the rule matched, the string a category promotion matches and the read-model key are one and the same; storing the raw field instead would leave a product priced as `Electronics` filed under something no storefront filter and no category promotion ever asks for.
- **What the caller logs.** `BasePriceCalculator.fromRules` returns the ids it compiled, in evaluation order, because a rule seeded with the wrong `type` is filtered out silently and the file is then priced without it, with the job green and the version unmoved. Logging the ids once per job makes a missing rule visible somewhere other than the prices, and answers "which rules produced this price" for ingestion.
- **An empty rule set is an error.** A set with no active ingestion rule left in it does not compile. Pricing a 500 000-row file at raw vendor cost, with no markup and no commission, and reporting the job completed is a loss with no alarm attached to it; stopping is loud and recoverable. Since the rules are seeded by a migration, a restore brings them back, so the only route into this state is an admin deactivating every rule. The error names both causes, and an import started in that state fails chunk by chunk until each chunk exhausts its failure budget. That is the intended answer rather than an oversight: deactivating every pricing rule is a decision to stop pricing, and an import that continued would write the catalogue at cost.
- **The composition here is not the promotion discount formula.** `apply()` folds rule adjustments into a vendor price; the single discount implementation REVIEW.md §1.3 protects belongs to the promotion module. A calculator must not copy this flooring logic, or there are two of them.
- **Loading.** The rule set is loaded once and cached for 60 s behind an injected clock, with the in-flight promise cached so a cold batch issues one query rather than one per row, and a failed load is not cached.
- **Database structures:** `ingestion_jobs` (file identity, counters, status), `ingestion_chunks` (byte range, `next_offset`, `lease_until`, `attempts` for resumptions and a separate `failures` counter that alone drives the terminal state), a partial unique index for one running job per vendor, `products.sku` unique for idempotent upserts, and `products.ingest_job_id` plus `products.ingest_source_offset` so duplicate SKUs across chunks resolve by `(job, position in file)` rather than by commit order, which keeps horizontal worker scaling safe.

### Failure modes defended against

- Timeout mid-chunk: loss bounded to one uncommitted batch; the next invocation resumes at `next_offset`.
- Duplicate delivery or two workers on one chunk: the lease and the compare-and-set make the second writer roll back instead of regressing the offset.
- A pricing rule that produces an impossible price: the row is rejected with the offending rule named and counted, rather than an exception aborting the surrounding batch.
- A rule set with no active ingestion rule in it — deactivated rows, a restore without the seed, or only promotion-layer rows: the compile throws, so the job stops instead of storing a whole catalogue at raw vendor cost with the job reported completed.
- Duplicate SKU inside a batch: deduped before the statement, so PostgreSQL never raises "cannot affect row a second time".
- Multi-byte text and CRLF: offsets are byte counts; a newline cannot occur inside a UTF-8 sequence, so lines decode safely.
- Memory: only one batch and the stream buffers are resident; no per-row events, no whole-file parse.
- Same file twice: the hash rejects it; a re-run after a crash converges to the same rows through the SKU upsert.
- Stuck job: an expired lease is visible as "stuck" and any worker can re-claim; a hand-off at budget end releases the lease before re-enqueueing, and the reconciler re-enqueues orphaned chunks; operators can pause, resume or abort.

### Trade-offs

- Rows for one SKU appearing in different chunks resolve by `(ingest_job_id, ingest_source_offset)`, not commit order, so out-of-order commits from scaled workers cannot regress a later row; the cost is two columns and one row-value comparison per upsert. **The guard orders by registration, not by data freshness**, and job ids are global while `ingestion_jobs_one_running_per_vendor` only serialises one vendor. So "an older file cannot clobber a newer one" holds within a vendor and by upload order only: two vendors whose files both carry SKU `X-1`, or one vendor uploading a backlog file after a fresh one, resolve to whichever was registered last. The skipped row is counted as processed and nothing logs it. Making it visible means counting guard-skipped rows into `rows_rejected`; making it correct means ordering on a file-supplied `generated_at` carried on `ingestion_jobs` rather than on identity. Neither is built here — the upsert that reads these columns is the ingestion worker's.
- **`ingestion_jobs.file_sha256` is unique globally and for ever, not per vendor.** Idempotency is content-addressed, so the same bytes can never be registered twice: two vendors sending a byte-identical file (a shared ERP export, or a header-only one) means the second gets a `409` carrying the first vendor's job id — a cross-tenant identifier in an error body (REVIEW.md 8.3b) and a legitimate upload permanently refused. A vendor whose catalogue is unchanged week to week cannot re-run last week's file at all. `unique (vendor, file_sha256)` keeps the idempotency property and removes the leak at no cost; it is recorded here rather than taken, because the key's scope is the owner's to set and `tests/integration/shared/db/schema.test.ts` currently pins the global shape as intended.
- **`failed` and `aborted` are terminal, and the sha lock outlives them.** A file that failed at chunk 37 for a reason outside itself — a wrong `pricing_rules` row, say — cannot be re-uploaded after the fix: the sha row still exists, so registration is a `409` pointing at the dead job, and `ingestion_chunks.job_id` is `ON DELETE NO ACTION`, so recovery is hand-written SQL across two tables. The recovery path is a `retry` mutation resetting the job's `failed` chunks to `pending` and reusing the existing sha row; it needs no DDL and belongs to the ingestion endpoints, not to this schema.
- **`chunks_done` is exactly-once only if the finish transition carries its own precondition.** The counter is incremented in the same statement that moves a chunk out of `running`, so the `UPDATE` must name the status it expects (REVIEW.md 2.3): a retry of an already-finished chunk must match no row rather than add a second increment. The column shape cannot enforce that — the writing statement does — so it is stated here alongside the hot-row trade-off in ADR-0003.
- The file must be immutable once registered and must not contain embedded newlines; both are stated as the file contract.
- A crash between commit and enqueueing `product.upserted` delays the read-model update until the reconciler runs.
- The seeded rules match a category by exact, case-sensitive equality (`Electronics`). A vendor file that spells a category differently is a row edit, not a code change, but nothing warns that it stopped matching until the priced rows are looked at.
- **A rule that runs and means the wrong thing is the class nothing here catches.** The compile probe fails a rule that cannot run — an unknown operator, a fact no vendor row carries — once, with the rule named. A rule that runs correctly and matches nothing (`electronics` for `Electronics`) or adjusts the wrong way (`-1500` for `1500`) compiles clean, passes the probe and prices 500 000 rows wrongly with the job green; so does one that drives every row below zero, which is then rejected one row at a time rather than stopping the job. `adjustCents` is deliberately unbounded above for the same reason: an impossible rebate can only be judged against a price. The missing defence is a count of fires per rule per chunk, where a compiled rule with zero fires over a whole file is the alarm; it belongs to the chunk processor, not here.
- **The probe walks raw JSON, so two narrow shapes read differently than they run.** `withoutPriorities` strips any key named `priority` at any depth, including one inside an operator's `value` object, so such a rule is probed as a slightly different rule than the engine runs; mirror image, the empty-group check rejects a legitimate `value: {all: []}`. Both are consequences of checking the condition tree as data rather than parsing it, and both are narrow enough to accept — the alternative is a second implementation of the engine's own condition grammar.
- **One file can be priced by two rule sets, and cannot be re-run.** Each worker caches a compiled set for 60 s behind its own clock, so an operator editing `pricing_rules` mid-import cuts over at a different moment in each process and chunks straddle the edit. The corrective re-upload is refused: `ingestion_jobs_file_sha256_unique` returns a `409`. Pinning the set for the life of a job — the job row storing the `pricing_rules_version` its first chunk compiled, a later mismatch failing the chunk as `fault: 'rules'` — is one column and one comparison, and belongs with the job row.
- **`pricing_rules_version` names an instant, not a rule set.** It is `max(updated_at)` of the active rules, so a `DELETE` does not move it and two different rule sets can share a version; and because `pricing_rules_name_unique` forbids a second row with the same name, every edit is an in-place `UPDATE` that destroys the previous body. "Which rules priced this row" is therefore unanswerable after the fact. An append-only shape — deactivate and insert rather than update — is the fix and is a migration's to make.
- **The engine queue is a process-wide lock per rule set, and costs nothing worth optimising.** Measured: 68 253 rows/s sequential against 73 276 with `Promise.all`, which buys no parallelism because the queue serialises anyway, and holds every queued row — 100 000 rows reach 258 MB RSS against a 256 MB container, 200 000 exhaust the heap. The correct caller shape is a sequential loop over a bounded batch; that is the chunk processor's contract.
- Locally the "serverless" unit is hosted by a BullMQ worker under Docker memory and CPU limits; the function body is the same, the trigger differs.

### Rejected alternatives

- Row payloads in queue jobs: 500 000 rows in Redis memory and no intra-chunk resume.
- `readline` with character offsets: drifts on multi-byte text.
- A single long-running import process: exactly what the consumption plan forbids.
- An RSS-based memory guard: Node RSS does not shrink, so it either never fires or always fires; batch size bounds memory instead.

## ADR-0006: Read model for flash sales (Scenario B)

**Status:** Accepted

### Context

A category promotion must affect tens of thousands of products the moment it is created, the listing endpoint sees massive read traffic while it runs, products added to the category mid-sale must be discounted automatically, and cancellation or expiry must restore prices promptly.

### Decision

**Pattern:** derive, do not store, on the write side; materialise on the read side.

- Creating or assigning a category promotion is one row and one `promotion.changed` event. Nothing touches product rows.
- The event handler scans the category by keyset in batches of 1 000, recomputes each product's applied promotion and effective price from PostgreSQL, and pipelines the read-model writes, one Lua compare-and-set per product (`HSET product:{id}`, `ZADD category:{c}`, `ZADD products:all`; ADR-0003). Listings are `ZRANGE ... BYSCORE` with offset and limit; detail is `HGETALL`.
- A new product's `product.upserted` recompute finds the active category promotion, so the product is born discounted; it is not visible in the storefront until its hash exists.
- Cancellation removes the delayed boundary jobs and emits an immediate recompute; scheduled starts and expiries fire as delayed jobs at the boundary.
- **Tools:** Redis sorted sets and hashes, BullMQ delayed jobs, one Lua compare-and-set script per product, pipelined. **Database structures:** `products (category, id)` index for keyset scans, the exclusion constraints from ADR-0004.

**What a storefront read may do.** The two read routes are the first consumer of this decision, and the rules they set bind every later one:

- **Redis or nothing.** A storefront route holds one client, on the read-model database, and no PostgreSQL connection to fall back to. A fallback query turns a read-model outage into a write-store outage: the load the read model exists to absorb arrives at the database exactly when it can least take it. `createApp` takes that client as a required argument rather than an optional one: an optional client is a process that boots clean, answers `404` on every product URL and passes every test, which is how the wiring went missing once in a merge.
- **Not ready and unreachable are one answer.** A completed full rebuild publishes `readmodel:ready`; until that key exists, and whenever the client cannot reach Redis, every storefront route answers `503` before the request is routed. Nothing in the body tells the two apart: the envelope is `{ error: { message } }` with no code field, because the status is the taxonomy (ADR-0009). The client runs with no offline queue, one retry and a one-second command timeout (`src/shared/read-model-client.ts`), so an unreachable server answers in a round trip instead of holding a socket until it times out; that timeout is client-side elapsed time, so it bounds this process's own event-loop lag as well as Redis. The retry hint rides the `headers` property ADR-0009 reserves for a `Retry-After`, and it is a band rather than a fixed number, so a fleet that met one outage does not come back in one second.
- **An absent member is a rebuild; an incomplete hash is a bug.** A category's sorted set and its product hashes are written separately, so a listing mid-recompute can name an id whose hash is already gone. That member is dropped from the page: one product must not take the rest of the page with it. **The drop is silent** — no log line and no metric — until the rebuild that can produce it exists, along with the counter that measures it; a rebuild that publishes members without their hashes therefore shows as short pages against an unchanged total, and nothing else. A hash that is present but missing a field is the opposite case — the writer wrote the product wrong — and it fails the request loudly rather than answering a price the store never held. What the writer has not written yet is skipped; what it wrote incorrectly is an error.
- **Depth is bounded at the boundary.** Redis skips an offset member by member, so a deep page walks the sorted set on a single-threaded server: the page size bounds the fan-out, not the scan. The maximum offset is part of the query schema and a page past it is a `400`, not a slow request discovered in production. A keyset cursor on `(score, id)` is the named upgrade, and it is the same shape the recompute will need to walk a category.

### Failure modes defended against

- Write amplification on the write store: zero product-row updates per flash sale.
- Read traffic reaching PostgreSQL: none. A product the detail route cannot find is a `404`, and the route does not ask whether an index still lists it. **The writer's contract is what keeps a listed member from outliving its hash**: a rebuild writes the hash before the `ZADD` and removes the member before the `UNLINK`, so the window the route would be detecting does not arise. Issue #12 inherits that contract, and a paid command on every miss to detect a state the writer must not produce is a guard against a failure nothing makes. An unready or unreachable read model is a `503`, at the gate and at every command after it.
- A deep page used as a cheap denial of service: refused by the schema before it reaches Redis.
- Out-of-order handlers (cancel then assign on one category): every read-model write is a compare-and-set on the `sourceReadAt` the recompute read at, so a later write cannot be overtaken by an earlier one (ADR-0003).
- Missed boundary: the reconciler sweeps promotions whose boundaries passed since its last successful sweep (persisted watermark, ADR-0007) and re-emits the event.
- Cold start: no `readmodel:ready`, so every storefront route answers `503` until a rebuild publishes it. **Redis loss is not yet defended against and nothing here triggers a rebuild**: the key is written to an append-only file on a persisted volume, so a restart reloads the flag and the hashes it certified together, and the storefront serves a finished sale's prices at `200` until something recomputes. The rebuild owns that key's lifecycle — unlink it before the sweep, set it last — and the story that writes the rebuild owns writing it that way.

### Trade-offs

- A recompute takes seconds over 50 000 products, so listing pages mix old and new prices while it runs. The atomic upgrade is building `category:{c}:new` and renaming it.
- One Worker on the `promotions` queue is the throughput ceiling, and a category recompute is the longest job on it. Adding consumers is the upgrade and needs the compare-and-set already specified.
- Offset paging can repeat or skip a product across a price change between two page requests, and depth is capped at an offset of 10 000. A keyset cursor on `(score, id)` is the upgrade.
- **The repeat-or-skip window is accepted, not inherited** (owner decision, 2026-09-13). A listing is ordered by the very value a sale changes, so a product whose price moves between two page requests can appear on both pages or on neither. It is accepted for this submission because the alternative is a cursor or a snapshot, which is its own story rather than a detail of this one. What a shopper is still owed, and what the cases assert: while prices are still, no duplicate and no skip; while prices move, every product shown is real and at a price that was true when its page was built, and every product whose price did not move appears exactly once across the pages.
- **The depth ceiling is shopper-visible on a large category.** A page beyond an offset of 10 000 is refused with a `400` rather than served slowly, and `total` still reports the whole catalogue — so on a 50 000-product category paging reaches the first 10 000 by design, and the rest needs a filter or the cursor above.
- `total` is a `ZCARD` taken outside the page's snapshot, so during a recompute it can disagree with the page a client received.
- A page taken during a recompute can come back shorter than its page size, because a member whose entry is gone is dropped rather than replaced.
- Stock is part of the read model and is therefore eventually consistent with it.
- Redis runs `--maxmemory-policy noeviction`, because this model has no TTL and no fallback; an evicting instance would answer 404 for live products while the ready flag still said ready.
- The readiness gate costs one extra command and one sequential round trip on every request, including the detail route. Caching it in process would serve an outage for as long as the cache lasted.
- The promotion pair is written together or omitted together, never as `''` or `null`: Redis has no null and ioredis stores both as the empty string, so a reader refusing them would fail every product without a promotion.
- `HSET` does not remove a field, so a cancelled promotion needs an explicit delete or the storefront names a finished sale beside a restored base price.
- The staleness a shopper can see is not measured, so "a few seconds" is an expectation rather than a bound.
- A bounded offset bounds one request rather than one client, and there is no rate limiter on these unauthenticated routes.
- An empty promotion name in the database arrives as half a pair and is refused with its page; the column has no non-empty check, and that check belongs to the story that writes promotions.
- A caller's bytes are never concatenated into a message an operator reads, so a wrong-typed index key is named only when this module composed it.

### Rejected alternatives

- Materialised `effective_price` column on `products`: 50 000-row updates per flash sale and a scheduled sweep for expiry.
- Read-time SQL pricing with a TTL cache: correct, but every cache miss is a sort over the category and scheduled starts are late by the TTL.
- Storing the promotions themselves as `pricing_rules` rows: see ADR-0004. The `pricing_rules` layer is used for promotions, but only to select between candidates; the promotions stay rows.

## ADR-0007: Safety net and operational recovery

**Status:** Accepted

### Context

The read model, the event queue and chunked ingestion each introduce a way for state to diverge or work to stall. The system must both repair itself and expose handles for an operator to intervene when a backlog builds.

### Decision

Automatic: BullMQ retries with exponential backoff and a kept failed set as the dead-letter queue; stalled-job recovery with `lockDuration` sized to the ingestion time budget; compare-and-set checkpoints so retries resume; `429` backpressure on imports above a queue-depth threshold; a category-scoped reconciler every five minutes (count comparison, sampled price verification, promotion-boundary sweep, ingestion orphan-chunk sweep) that enqueues a scoped rebuild on mismatch; a cold-start full rebuild gated by `readmodel:ready`; workers that finish their batch and exit when heap use crosses a limit, restarted by the container runtime; every handler logs and rethrows so failures are recorded, never swallowed.

Manual, under `/api/admin` and Bull Board: queue statistics, pause and resume per queue, drain, dead-letter retry and discard, per-import pause, resume and abort, and scoped or full read-model rebuild, recomputing each entry through the write script, with `SCAN` and `UNLINK` on the read-model database only for ids PostgreSQL no longer has (ADR-0003).

Alarms: the API and workers expose Prometheus metrics (`prom-client`); a `monitoring` compose profile runs Prometheus and Grafana with a provisioned dashboard and alert rules for queue depth, dead-letter jobs, read-model drift, API p95 latency, 5xx rate, worker memory, stuck ingestion chunks and health. Alerts are visible in Grafana Alerting; notification channels are Grafana configuration.

### Consequences

- Any single failure (worker crash, lost event, expired lease, Redis restart) converges without operator action within one reconciler period, with the one exception ADR-0003 states: a lost `promotion.changed` for a cancel can fall outside the boundary sweep, and then converges by sampling instead.
- Operators have a small, orthogonal set of levers: stop intake, stop consumption, retry or discard failures, rebuild a scope.
- The read-model and queue databases are separate, so no maintenance action can destroy queued work.

### Trade-offs

- The promotion boundary sweep runs from a persisted watermark (`reconciler_state.last_boundary_sweep_at`), so an outage of any length is caught up on the first run back, at the cost of one extra row and one write per run.
- BullMQ ignores an `add` for a job id it still holds, and `removeOnComplete: 1000` is a count rather than a duration, so whether a fired boundary job is still resident depends on the completion rate. Nothing is allowed to depend on the answer: the reconciler's sweep re-emits `promotion.changed` with no job id, and the deterministic `promo:{id}:{activate,expire}` ids are used only to schedule and to cancel a future boundary. Write-once also means boundaries are immutable after assign: a branch that lets `starts_at` or `ends_at` be edited has to remove the jobs before re-scheduling, or the old boundary fires and the new one is dropped. The two colons in that id are load-bearing: bullmq 6.3.4 rejects a custom job id containing a colon unless it splits into exactly three parts, a compatibility carve-out its own source marks for removal in the next breaking change, so `promo:{id}:{boundary}` passes by arithmetic rather than by a documented API. A major upgrade that tightens it makes `publish` throw after the promotion has already committed; the escape is `promo-{id}-{boundary}`. What catches such an upgrade rather than production is the integration test that schedules a boundary and asserts the job it stored (`tests/integration/shared/queue/event-queue.test.ts`): a bullmq that rejects the format fails the `add` in that test.
- The dead-letter set is deliberately unbounded (`removeOnFail: false`): a poisoned job must survive its retries and stay inspectable. The bound is operational rather than structural — the Grafana "any failed job" alert fires on the first one and `POST /api/admin/dlq/retry` or `discard` drains it — so a failure that retries thousands of jobs, such as PostgreSQL being unavailable through a 500 000-row import, grows Redis until an operator acts. Both stores share an instance, so that pressure reaches the read model even though the logical databases are separate.
- The price check in the reconciler is sampled (`max(50, 1 %)` of a category per run, capped at 500), so a single wrong price can survive a run; the exact count comparison and the resampling on every run bound that exposure to minutes, and the manual rebuild remains the override.
- A five-minute reconciler period is the worst-case repair time for a lost event. Shorter periods cost PostgreSQL reads; the sampled check keeps each run cheap.
- A drain deletes waiting work; it requires an explicit confirmation parameter.
- Alerting lives in Grafana rules rather than application code, so thresholds can be tuned without a deploy but are not unit-tested; the metrics that feed them are.

### Rejected alternatives

- Full rebuild on any drift: unnecessary load; scoped rebuilds are sufficient.
- `FLUSHDB` for rebuilds: would erase the queue when it shares the instance.

## ADR-0008: Source layout and naming inside a module

**Status:** Accepted — owner decisions of 2026-09-12 and 2026-09-13, enforced by REVIEW.md 8c

### Context

The first two modules were reviewed file by file, and the same three findings came back on each: several declarations in one file, directories named for a kind of syntax rather than a job, and exports whose names read as data when they were behaviour. REVIEW.md 8c says what a reviewer rejects; this record says what the layout is and why.

### Decision

**Layout.** A modular monolith: one directory per module under `src/modules/`, and inside a module the directories are named for a role, opened only when a file goes in:

```
src/modules/<module>/
  domain/        the module's behaviour as classes (8c.9); imports no store and no framework
    dto/         every shape those classes operate on: types, interfaces, enum-like aliases, zod schemas
  queries/       one class per read use case: collaborators in the constructor, `execute(input)`
  commands/      one class per write use case, same shape
  db/            the store gateway: the keys or SQL, and what a failed call means
  http/          routes, handlers, request schemas (zod)
  events/        the events this module owns, one payload schema per file, and one `<Event>Handler` class per event it consumes: collaborators in the constructor, `handle(payload)`
src/shared/
  config.ts
  db/            client, migrator, migrations (one journal, owned by api — ADR-0003)
  http/          error handler, request validator, the pino-http middleware (no error type: errors are `http-errors`, ADR-0009)
  queue/         the BullMQ queues and their names; generic over a catalogue it is given
  graceful-shutdown.ts
  logger.ts
  read-model-client.ts   the storefront's ioredis client and its failure posture (ADR-0006)
src/events/      event-registry.ts and event-routing.ts: the application's catalogue, plus the one payload whose module does not exist yet
tests/
  unit/          mirrors src/, one test file per source file
  integration/   real PostgreSQL and Redis
```

A use-case class holds its collaborators and its decision: the miss that becomes a 404, the mapping to a view, the classification of a failure. A route calls exactly one of them and decides nothing, which is the checkable form — a route branching on what a store answered means the use case is still in the route. A command takes a repository, so it cannot live in `domain/`, which imports no store; that is why the two folders exist rather than one. The queue side is the same shape: a worker entry point in `src/workers/` dispatches to one `<Event>Handler` and decides nothing, so a dispatcher branching on what a payload means has not handed the use case over either.

**`shared/` is infrastructure only.** Nothing under `src/shared/` carries a business noun in its name: configuration, the database client and migrator, HTTP plumbing and the logger live there; `promotions`, `products`, `pricing_rules` do not. A table's Drizzle definition belongs to the module that owns the table, in `src/modules/<module>/db/schema/<table>.ts`, and `drizzle.config.ts` globs every module's and worker's `db/schema/` rather than one directory. The twelve schema files — six tables, five enums and the `active_promotions` view — have moved out of `src/shared/db/schema/`, the barrel that re-exported them is gone, and `createDb` no longer takes a schema object — nothing assembles every table in one place any more. `reconciler_state` went to `src/workers/reconciler/db/schema/`, because the reconciler owns it and is not a module. The migrations stay in one place under `shared/db/`, because there is one journal and one process applies it (ADR-0003). Two consequences: a table two modules read is owned by one of them and imported by the other (`pricing_rules` belongs to `pricing`; the promotion resolver imports it for its precedence rule), and a table everything references is its own module (`products` is the `product` module, which `promotion` and `pricing` may import, while those two still import nothing from each other). Without this rule `shared/` is where every table lands because it is the path of least resistance, and it grows into the one directory the module split was meant to prevent.

`domain/dto/` is the one directory named for what it holds rather than for a job. `domain/` beside it holds behaviour only, as classes. `dto/` holds every shape, not only type aliases: a zod schema is a shape that can check itself, so the pricing module's `vendor-row-facts.ts` and `adjustment-event.ts` are dto. An event payload is not: it sits in `events/` beside the handlers, defined once in the module that owns the event's meaning and imported by anyone else who needs it. That is the whole of what one module may import from another: shapes — a table's schema from the module that owns the table, a payload from the module that owns the event's meaning — and never a function. `domain/` itself is behaviour only. `adjustment-event` keeps the library's word for a rule's action; it is not a system event. With types and functions at one level a reader could not tell a data shape from the logic over it without opening the file; the split is taken for that reason and for nothing else — `http/`, `db/` and `events/` are not divided further. Promotion and pricing are separate modules that import nothing from each other (ADR-0004, ADR-0005).

**An event payload lives in the module that owns the event's meaning, not the one that emits it, and the catalogue that collects them sits above both.** `product.upserted` is `src/modules/product/events/product-upserted.ts`, `promotion.changed` is the promotion module's, `chunk.process` the ingestion module's; `readmodel.rebuild` is the `storefront` module's (`src/modules/storefront/events/readmodel-rebuild.ts`), because only the read side knows what a rebuilt entry is, and nothing emits it today; `reconciler.run` is defined in `src/events/` until the reconciler is a module. `src/events/event-registry.ts` maps every name to its schema and `src/events/event-routing.ts` to its queue, and neither lives in `shared/`: modules depend on `shared/`, never the other way, so a registry there would invert the direction and the first module importing the queue would close a cycle. `src/shared/queue/event-queue.ts` is therefore generic over the catalogue, which `src/server.ts` passes to `EventQueue.connect`. The direction is `modules → shared`, `events → modules + shared`, `server → events`. `eventRouting` is `satisfies Record<EventName, QueueName>`, so an event added without a queue is still a compile error, and `EventName`/`EventPayload` derive from `typeof eventRegistry`, so the types are as tight as when the catalogue was a constant in `shared/`.

**A comment is for the reader who is stuck, and it is simpler than the code.** Code that reads on its own has no comment. Code that does not gets one plain sentence, never a paragraph; a paragraph means the code needs a better name or a smaller method, and the reasoning belongs in this record. A comment harder than the code it sits on is a defect (REVIEW.md 8b.1a).

**One exported declaration per file, and the file is named for it.** A file holds one class, interface, type alias or function, plus the private helpers only it uses. It is one export per file, not one declaration: a type with one reader is written in that signature and a constant with one reader is a non-exported constant in its reader's file, so the tree holds no file whose only reason is the rule. The name is the same in the file, the export, the ADR and the spec — and in the test: `tests/` mirrors `src/` one file to one file, `effective-price-calculator.ts` is tested by `effective-price-calculator.test.ts` at the same path under `tests/unit/`, and its top-level `describe` is the export's name.

**Behaviour is a class.** Every unit of behaviour in a module — a domain rule, a repository, a service, a loader, a job processor — is a class named for its role, taking its collaborators through the constructor and reached through an interface wherever a second implementation or a test stand-in is plausible. The rule that keeps this honest: a class holds state, or holds collaborators, or implements an interface; one that does none of the three is a function wearing a class, and stays a function. An abstract base exists only once it has two concrete subclasses; there are no static-only utility classes and no class that knows the whole module. A helper that serves one class is a private method of that class (Fowler's Extract Method), not a file: a file exists for a second user, and one declaration per file (8c.2) counts exports, not private methods. Decided on 2026-09-13, after the first two modules had been written as free functions: the pricing module was carrying per-engine state in a `WeakMap` because it had no object to put it on, and the promotion calculator was reaching its collaborator, the set of discounts, as an import. Both are what a class is for. The 2026-09-12 decision this replaces was against an abstraction with one user — a shared base for promotion and ingestion pricing — not against classes.

**Naming.**

- A class is the noun phrase of its role: `EffectivePriceCalculator`, `BasePriceCalculator`, `BasePriceCalculatorCache`. Its methods start with a verb: `calculate`, `fromRules`, `current`. No name here carries `Engine` or `Rule`: `json-rules-engine` exports `Engine` already, and `pricing-rules.ts` is the table.
- An interface is the noun of its role, as a reader would say it: `Discount`. Each implementation is the variant plus that noun: `PercentageDiscount`, `FixedDiscount`. A suffix on the interface (`DiscountCalculator`) is noise every implementation then has to repeat or drop.
- A private method or a free helper starts with a verb: `validateBasePriceAndDiscount`, `withoutPriorities`. One named for the value it returns reads as a property.
- A file carries the whole name of the one thing it exports: `effective-price-calculator.ts`, `discount.ts`, `percentage-discount.ts`. Never a bare verb with no subject (`validate.ts`).
- Directories are never `models/`, `types/`, `interfaces/`, `classes/`, `utils/` or `helpers/`; a concept is what a directory is for, a syntax kind is not.

### Consequences

- More files, each short; the tree is the index, and a file name answers "what is this" without opening it.
- A test of a property of the whole tree, with no source file to mirror — that `runMigrations` has one importer, that the migration journal is ordered — lives under `tests/unit/` at the path of what it guards, named for the property; 7.7 asks for one test per source file and this is the one shape that rule cannot reach.
- Each table's Drizzle definition sits in the module that owns it — `product` for `products`, `promotion`, `pricing`, `ingestion` — and `reconciler_state` under `src/workers/reconciler/db/schema/`, because the reconciler owns it and is not a module. `src/shared/db/` keeps the client, the migrator and the one journal. There is no barrel re-exporting every table and `createDb` takes no schema object, so nothing assembles the whole catalogue of tables in one place.
- The promotion and pricing modules were written as free functions before this record and are converted rather than grandfathered, because an exception survives longer than the reason for it: `EffectivePriceCalculator` (constructor takes the `Discount` set; the lookup is inline in `calculate` and `validateBasePriceAndDiscount` is a private method, replacing `discount-calculators.ts`, `discount-calculator-for.ts` and `pricing-input-error.ts`), `PercentageDiscount` and `FixedDiscount` implementing `Discount`, `BasePriceCalculator` (the engine run queue becomes a field, replacing the `WeakMap`), `BasePriceCalculatorCache` (the cache becomes a field). Files and test files follow the class names (7.7).
- A class reads top-down: fields, constructor, public methods, private methods. The interface a caller uses is the first thing on the screen; the mechanics come after it. ESLint `@typescript-eslint/member-ordering` holds the order, so a review never has to.
- `REVIEW.md` 7.7, 8c.2, 8c.3, 8c.7, 8c.8, 8c.9 and 8c.10 carry the enforceable form, one sentence each with a pointer here; the reasoning lives in this record only, so a change here changes them in the same pull request.

## ADR-0009: HTTP boundary contract — `/api` prefix, strict validation, one JSON error envelope

**Status:** Accepted

### Context

Every endpoint in ADR-0003 to ADR-0007 has to agree on where it is mounted, how a request is validated and what a failure looks like, or each story invents its own and a client sees three shapes of the same error.

### Decision

- **Prefix.** Everything is mounted on an `express.Router()` under `/api`, including the liveness probe, which moves from `GET /health` to `GET /api/health`. The operator's API routes are inside both, as the design spec's section 9 places them under `/api/admin`: `GET /api/admin/queues/stats` answers under the prefix and its failures carry the same `{ error: { message } }` envelope. Outside sits what is not an API route — the same section puts Bull Board at `/admin/queues`, and a Prometheus scrape reads a text exposition format rather than an envelope, so `GET /metrics` mounts outside both when it is written. Three costs come with moving the operator surface inside: it is reachable by any caller, which the old wording implied it was not — no route in this API is authenticated and the case study puts authentication out of scope, so an admin _read_ is no more exposed than the unauthenticated promotion _writes_ beside it, and the day one of them needs a caller check they all do — with one asymmetry, that a request costs about twenty Redis commands on the queue database, is not rate limited, and shares that Redis with publishing, so a sustained unauthenticated loop reaches the writes through their own 2 s bound; the response is a set of independently read values rather than a snapshot, so `waiting` and `oldestWaitingAgeSeconds` can disagree by one poll, the way section 5.5 already treats the storefront's paging window; and detection is whatever an operator looks at, because there is no history and no scrape until the monitoring half of #18.
- **Validation at the boundary.** `validate({ body?, query?, params? })` takes zod object schemas, calls `.strict()` on them once at route construction, and replaces each declared part with the parsed value. A schema's own message is not a response: the rejection says `Invalid request <part>` and nothing else, so a message a caller has to read is raised by the handler rather than written into a schema. The body is a message; the diagnosis is the log line, which carries the same sentence under `reason`. An unknown field is a `400`, not a silently ignored client typo. `req.query` is a getter in Express 5, so the parsed value is installed with `Object.defineProperty`.
- **Errors are `http-errors`, used as its README documents.** `createError(status, message, properties)`; `expose` decides what a client may read, and it is already `false` for a 5xx unless the raiser says otherwise, so operator prose is withheld because the library withholds it rather than because someone remembered to. `headers` carries a `Retry-After`. We keep no error classes and no code-to-status table: the status is the taxonomy. A class extending the constructor is allowed only where the same raise — status, message and properties — would be rebuilt at several sites. One qualifies: `ReadModelUnavailableError` (`src/modules/storefront/db/read-model-unavailable-error.ts`) extends `createError.ServiceUnavailable` and carries the `Retry-After` band of ADR-0006, because the read gate and every read-model call raise the same 503. Nothing else raises the same error twice, so no other class is written.
- **A foreign error is trusted only when the library itself recognises it** — `createError.isHttpError`, which wants `status` and `statusCode` agreeing and a boolean `expose`. Anything else answers `500` with `Internal server error`, message and all, rather than the handler guessing at a half-shaped error.
- **`100kb` JSON body cap.** Multipart does not pass through this layer, so the vendor upload brings its own bound.

### Consequences

- A client branches on the status, not on a code field: the envelope is `{ error: { message } }`. body-parser's own 4xx messages reach the caller wherever they describe the caller's own request — "unsupported charset", "request entity too large". Its parse failure (`type === 'entity.parse.failed'`) is the one exception: that message quotes the offending bytes and the parser's position, so the handler answers `Invalid JSON body` and puts the original under `reason` in the log. One `type` check in `src/shared/http/error-handler.ts`, not a code-to-status table.
- The boundary lives in `src/shared/http/`, so a story adds a route rather than an error convention.
- Moving the probe to `/api/health` had two consumers, not one: the README and the `api` healthcheck in `docker-compose.yml`, which was left fetching `/health` and would have hung `up --wait` rather than failing. `tests/unit/docs/compose-healthcheck.test.ts` reads the URL out of compose and calls it, so the two cannot drift apart again (REVIEW.md 13.12).
- REVIEW.md 8.3b used to allow one stored identifier through the envelope, `details.conflictingPromotionId`. Dropping `details` leaves nowhere to carry it, so the carve-out fell away rather than being overruled, and the rule and this record were corrected together.

### Trade-offs

- A library's wording reaches the caller wherever that library marks it exposed, so body-parser's and any future middleware's 4xx messages are part of the public surface and are read once when the middleware is mounted. Reading one and finding it unfit costs a named exception in the error handler, as the parse failure did; what is given up is that the handler now knows one library's error `type`, which is the narrowest form of the coupling this record otherwise refuses.
- Validation costs one `safeParse` per declared part per request; the read-path story budgets against that rather than against the parse alone.
- Dropping `details` gives up machine-readable failure detail entirely, not one field. A client that later needs to branch on more than a status has no place to read it, and adding one is a new decision about the envelope — every endpoint's error shape at once, and a version of it for callers already parsing `{ error: { message } }` — rather than a field added to a structure that is already there. Acceptable because no client of this API parses an error beyond its status today, and a status plus a sentence is what an admin screen renders.

## ADR-0010: Structured logging with a validated correlation id

**Status:** Accepted

### Context

A request does not end at the HTTP response: it emits an event a worker picks up later, so diagnosing one means joining an API line to a worker line. `console.log` gives neither structure nor a join key.

### Decision

- `src/shared/logger.ts` exports the pino root logger and `src/shared/http/http-logger.ts` the `pino-http` middleware, mounted first in `createApp` so every later handler has `req.log`.
- **Correlation id.** Taken from `x-request-id` only when it matches `^[A-Za-z0-9._-]{1,128}$`, otherwise generated. The header is untrusted input: a newline forges log lines and a CR injects a response header. It is echoed back and bound as `reqId` on every line.
- **Narrowed serializers.** `req` is `{ id, method, path }` and `res` is `{ statusCode }`, so headers, body and query string are never serialised and no credential reaches a line.
- **The stack goes to the log and never to a response.**
- **No `console`.** Every line the process emits is JSON with the same fields.

### Consequences

- A grep on one `reqId` returns the whole request, provided the caller's id is unique, which is the caller's responsibility once it supplies one.
- A 4xx logs at `warn` with its status, and so does a 5xx carrying a `Retry-After`, which is an operating condition rather than a fault; every other 5xx logs at `error` under `err`, which makes real 500s an alertable signal rather than noise.
- The id is the join key the queue boundary will have to carry. It is not implemented: every payload schema is a `z.strictObject`, so an id attached by a producer throws inside `publish`, and adding it is a change to all five contracts.

### Trade-offs

- A diagnosis needing a request header or query string has to reproduce the request rather than read it back.
- pino's serializer walks `cause`, so a driver error's message and every wrapper around it reach the log line whole — the failing statement and its bound parameters with them. No route at this layer touches a database; the first story that queries PostgreSQL owns reducing a driver error against its real shape.
- A caller-supplied id is accepted, not verified to be unique, so a fleet sending one constant id collapses onto a single `reqId`.
