# End-to-end cases for #7 — Event contracts and BullMQ setup with retry, backoff and dead-letter queue

Derived from the acceptance criteria of issue #7 (Covers: A3, B1, B4, ADR-0003).
No case here was taken from the implementation.

This story describes the event-bus mechanism, so every case is a probe: none of
the three people in the system (vendor, admin, shopper) appears in any criterion.

### 7-1

- Actor: none (probe)
- Covers: criterion 1 of #7
- Precondition: event catalogue, `src/shared/queue/catalogue.ts`
- Given: the catalogue
- When: a producer emits `product.upserted`, `promotion.created`,
  `promotion.assigned`, `promotion.activated`, `promotion.cancelled`,
  `promotion.expired` or `ingestion.chunk` with a payload that does not match the
  event's schema
- Then: the emit is rejected by zod validation at runtime
- Measure: none

### 7-2

- Actor: none (probe)
- Covers: criterion 3 of #7
- Precondition: Redis DB 1, queues `events` and `ingestion`
- Given: queue names
- When: workers connect
- Then: they use Redis DB 1 and the `events` and `ingestion` queues only (no
  BullMQ keys exist on DB 0, and no queue key other than `events` and
  `ingestion` exists on DB 1)
- Measure: none

### 7-3

- Actor: none (probe)
- Covers: criteria 1 and 3 of #7
- Precondition: queues `events` and `ingestion`, Redis DB 1
- Given: the catalogue
- When: a producer emits each of `product.upserted`,
  `promotion.created|assigned|activated|cancelled|expired` and
  `ingestion.chunk` with a valid payload and a consumer drains the queue
- Then: every event round-trips and each payload is validated with zod at runtime
- Measure: none

### 7-4

- Actor: none (probe)
- Covers: criterion 4 of #7
- Precondition: `scheduleAt(queue, name, payload, at)`
- Given: a delayed job request
- When: `scheduleAt(queue, name, payload, at)` is called twice with the same
  arguments for an instant 5 s ahead
- Then: the job is delayed to that instant and, having a deterministic `jobId`,
  the duplicate is deduplicated — one job runs, and it runs at `at`
- Measure: delivery instant over 3 runs, fails if the job runs before `at` or
  more than 1 s after it

### 7-5

- Actor: none (probe)
- Covers: criterion 2 of #7
- Precondition: queue `events`, BullMQ failed set
- Given: a handler that throws
- When: the job fails
- Then: BullMQ retries 3 times with exponential backoff (1 s base) and the job
  then stays in the failed set (DLQ) with its error
- Measure: attempt timestamps over 1 run — 3 retries at roughly 1 s, 2 s, 4 s
  after the preceding attempt, fails if the attempt count is not 4 in total, if
  any gap is under its nominal value, or if the job is not in the failed set with
  its error afterwards

### 7-6

- Actor: none (probe)
- Covers: criterion 3 of #7
- Precondition: queue `events`, `removeOnComplete`
- Given: queue names
- When: 1 100 jobs complete on `events`
- Then: `removeOnComplete` keeps the last 1 000 jobs
- Measure: completed-set size after the run, fails if it is not 1 000
