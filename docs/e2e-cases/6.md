# Case file: issue #6 — HTTP skeleton: /api prefix, validation, JSON errors, correlation-id logging

Derived from the acceptance criteria of issue #6, not from the implementation.
Covers: R8.

Ids follow the order the criteria appear in the issue and never change. The
cases below are ordered cheapest-first, so a run fails early; that is why the
ids are not in ascending order.

Every route on this branch is mounted under `/api`. No database, queue,
product route or promotion route exists on this branch yet, so any case whose
precondition is one of those is expected to skip until the story that brings
it lands.

### 6-5

- Actor: shopper's client (and the platform's uptime probe) checking the API is up
- Precondition: GET /api/health
- Given: the existing health route
- When: called at `/api/health`
- Then: it returns 200, and the root `/health` path is gone (a request to `/health` must not return 200)
- Measure: none

### 6-2

- Actor: shopper whose client requests a path the API does not serve
- Precondition: the Express app's not-found handler, reachable at any unmounted path under `/api`
- Given: an unknown route
- When: requested
- Then: `404 { error: { code: 'NOT_FOUND', message } }`, as JSON with a JSON content type, not Express' default HTML error page
- Measure: none

### 6-4

- Actor: admin tracing one of their own requests through the logs after a failed flash-sale change
- Precondition: the correlation-id middleware plus any route that reaches it; exercised against GET /api/health on this branch
- Given: a request with `x-request-id`
- When: handled
- Then: the same id is echoed in the response header and appears in every log line emitted while handling that request; when the request carries no `x-request-id`, a UUID is generated and echoed the same way
- Measure: none

### 6-3

- Actor: admin whose action fails, who needs a truthful status and code back rather than a leaked stack trace
- Precondition: the error middleware, plus a route that throws `AppError(status, code, message)` and a route that throws an unexpected error. No domain route on this branch throws either yet, so this case waits on the first story that brings a real route, unless this branch mounts a deliberate fault-injection route.
- Given: a thrown `AppError(status, code, message)`
- When: it reaches the middleware
- Then: that status and that code are returned to the client; an unexpected (non-`AppError`) error instead becomes `500 { error: { code: 'INTERNAL' } }` with no internal detail in the body, and is logged with the stack
- Measure: none

### 6-1

- Actor: vendor or admin posting a malformed payload, who needs to be told which field is wrong instead of a generic failure
- Precondition: any route with zod validation on body, query or params. WAITS: no product, promotion or upload route exists on this branch, so this case skips until the story that mounts the first validated route lands.
- Given: any route
- When: the body, query or params fail zod validation
- Then: the response is `400 { error: { code: 'VALIDATION_ERROR', message, details } }`, with `details` naming the offending field(s)
- Measure: none
